# Веб-сайт гильдии

Техническая основа: React 19, Vite, TypeScript strict, TanStack Router, Query
и Form, zod, shadcn/ui (Radix), Tailwind CSS 4. Backend — Supabase Free (одна
Edge Function `api`, Kysely и postgres.js), frontend — GitHub Pages с
собственным доменом. Отдельный сервер приложения не требуется. Полный
обязательный перечень инструментов — раздел «Обязательный стек» в
[AGENTS.md](AGENTS.md): одна задача решается одним способом.

Реализованы оболочка, регистрация, вход, восстановление пароля, личный
кабинет, а также заявки (прямой приём или отказ, новая заявка после отказа),
состав клана с чтецами и таблица аккаунтов с ролями. Голосования, события,
торговля, колокольчик уведомлений и боты будут отдельными задачами.
Прототип находится в `prototype/` и не переносился в новое приложение.

## Запуск

Нужны Node.js 24 LTS с npm 11 или 12 и Git. Использованная при инициализации
версия npm указана в `packageManager`; CI использует именно её.

```sh
npm run clean-install
npm run dev
```

`npm run clean-install` выполняет `npm clean-install`: удаляет `node_modules` и
устанавливает зависимости строго по lockfile. Перед запуском остановите
серверы разработки и другие процессы проекта.

Адрес: `http://127.0.0.1:5173/#/`. Для старта не требуется `.env`, аккаунт
Supabase или Docker. Оформление — по прототипу ([дизайн-система](docs/design-system.md)).

Если системного npm нет, в текущем локальном рабочем каталоге подготовлена
игнорируемая копия `.tools/bin/npm.cmd`. Она доступна только на этой машине,
не входит в репозиторий и предполагает доступный `node` в PATH.
При обычном клонировании следует установить Node.js вместе с npm.

## Окружение и секреты

Создать локальный `.env` из шаблона:

```powershell
Copy-Item .env.example .env
```

Требуемое владельцем имя шаблона — `.env.example`. Это текстовый список
переменных, не зашифрованный файл. В нём разрешены только пустые значения.

Для подключения frontend к Supabase заполнить **обе** публичные переменные:

- `VITE_SUPABASE_URL` — HTTPS origin проекта.
- `VITE_SUPABASE_PUBLISHABLE_KEY` — ключ вида `sb_publishable_…`.

Для локального Supabase разрешён HTTP на loopback-адресе. Legacy JWT-ключи
в качестве браузерной конфигурации не поддерживаются: использовать новый
publishable key. Без обеих настроек ленивый клиент возвращает `null`.

Все значения `VITE_*` публичны и попадают в браузер. Добавление неизвестного
имени с этим префиксом останавливает запуск и сборку до обновления явного
списка разрешений в `src/lib/supabase/config.ts` и шаблона окружения.

Токены Telegram, MAX и VK нужны только при реализации соответствующих ботов.
Локально хранить их в `.env`; для опубликованных функций — в Supabase Secrets.

### Первый администратор

Первый аккаунт создателя назначается администратором закрытой командой (Q-32):

1. Зарегистрироваться на сайте и подтвердить email кодом; на экране
   «Завершите регистрацию» остановиться (профиль не создаётся).
2. Выполнить команду (классы — `slug` из справочника, например `mage`):

```sh
npm run admin:bootstrap -- --email you@example.com --nickname Ник --name Имя --class mage
```

Без `ADMIN_DATABASE_URL` команда работает с локальным Supabase; для облачного
проекта строка подключения задаётся только в локальном `.env`. Повторный
запуск отклоняется, если администратор уже есть; назначение пишется в аудит.

### Постоянные события по расписанию

Четыре еженедельных события создаёт задание Supabase Cron
`events-ensure-weekly` каждый понедельник в 00:00 МСК (Q-42). Задание вызывает
функцию `api` (`events/ensure-weekly`) с заголовком `x-cron-secret`. Адрес и
секрет берутся из Supabase Vault, в миграции их нет; без них задание ничего
не делает, а офицер создаёт выпуски кнопкой «Создать постоянные события
недели». Для облачного проекта (этап 12), одно и то же случайное значение:

1. `EVENTS_CRON_SECRET` — в Supabase Secrets функции (`supabase secrets set`).
2. В SQL-редакторе облачного проекта:
   `select vault.create_secret('<секрет>', 'events_cron_secret');` и
   `select vault.create_secret('https://<ref>.supabase.co', 'events_cron_api_url');`.

Секрет даёт только право запустить выпуск постоянных событий; служебный
ключ Supabase для расписания не используется. Локально задание по
расписанию не нужно: тесты вызывают операцию напрямую.

### Telegram-бот

Привязка аккаунта и анонсы в Telegram (этап 13,
[требования](docs/requirements/19-telegram.md)). Без переменных бота сайт
работает, а кабинет и «Рассылка» показывают, что Telegram не подключён.

Локально используется **отдельный тестовый бот** (Q-95): у бота один вебхук,
и туннель переключил бы на себя рабочего бота.

1. Создайте бота в [@BotFather](https://t.me/BotFather) и заполните в `.env`
   `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` (без @) и
   `TELEGRAM_WEBHOOK_SECRET` (32+ символа `A-Z a-z 0-9 _ -`). Необязательно —
   `SITE_URL` для ссылки в ответах бота.
2. `npm run supabase:functions` — функции читают `.env`. После правки кода
   функции перезапустите команду: при `policy = "per_worker"` горячей
   перезагрузки нет, зато фоновое обновление сообщений доделывается.
3. В соседнем терминале — `npm run telegram:dev`. Скрипт при первом запуске
   скачивает закреплённую версию `cloudflared` в `node_modules/.cache`,
   открывает быстрый туннель Cloudflare без аккаунта и ставит вебхук
   тестового бота на него. Ctrl+C снимает вебхук и закрывает туннель.

Новый адрес `*.trycloudflare.com` локальный DNS macOS первые минуты может
не находить; Telegram это не мешает.

Для облачного проекта (этап 12) токен, имя бота, секрет вебхука и `SITE_URL`
задаются в Supabase Secrets, затем вебхук рабочего бота регистрируется один
раз: `npm run telegram:webhook -- --functions https://<ref>.supabase.co/functions/v1`
(`--delete` — снять). Значения берутся из `.env` и не печатаются.

### Письма Auth

Адрес при регистрации и сброс пароля подтверждаются шестизначным кодом из
письма. Локально письма не отправляются, а попадают в Mailpit:
`http://127.0.0.1:54324`. Шаблоны — `supabase/templates/`.

Для писем выбран Resend. Переменные `AUTH_SMTP_HOST`, `AUTH_SMTP_USER`,
`AUTH_SMTP_PASS` (API-ключ Resend — секрет), `AUTH_SMTP_ADMIN_EMAIL`
(подтверждённый адрес отправителя) и `AUTH_SMTP_SENDER_NAME` описаны в
`.env.example`; `supabase/config.toml` читает их через `env(...)`, но SMTP
локально выключен (`enabled = false`). Для разовой локальной проверки Resend
заполните `.env` и временно включите SMTP, не коммитя это изменение.
Подключение домена и настройка облачного проекта — этап 12.
Не передавать серверные ключи в Vite, GitHub Pages или публичные Variables.
GitHub Actions Secrets использовать для будущих защищённых CI-операций.

`npm run security:check` проверяет исключение env-файлов из Git, пустые
значения шаблона и известные форматы секретов в рабочих файлах, индексе Git
и `dist/`. Сканер не
заменяет просмотр diff и не гарантирует обнаружение произвольных токенов.

Браузерные тесты работают по сборке, подключённой к локальному Supabase, на
desktop и mobile; коды из писем берутся из Mailpit:

```sh
npm run supabase:start
npx playwright install chromium
npm run build:e2e
npm run e2e:functions
npm run test:e2e
```

`npm run e2e:functions` держать запущенным в отдельном терминале: это
`supabase functions serve` с выдуманным ботом Telegram, чьи вызовы Bot API
идут в фальшивый сервер `e2e/fake-telegram.ts` (его поднимает Playwright).
Настоящий бот из `.env` в сценариях не участвует.
Сценарии заявок и членства (`e2e/applications.spec.ts`,
`e2e/membership.spec.ts`) создают кандидата через Auth API и Mailpit без
интерфейса, а офицера и администратора — прямой записью в локальную БД.
Для ручной проверки входа в `npm run dev` сначала выполнить
`npm run supabase:env`.

На Linux для первоначальной установки браузерных системных зависимостей
может потребоваться `npx playwright install --with-deps chromium`.
Артефакты и трассы не коммитятся. Проверки нового приложения не запускают
тесты из `prototype/`.

## Структура

```text
src/
  app/                  # Провайдеры, router, оболочка, заставка, роли
  routes/               # Только объявления маршрутов
  features/<домен>/     # Страницы и логика: auth, registration, account,
                        # applications, roster, admin, catalog, home,
                        # not-found, sections, dev
  components/ui/        # Компоненты shadcn/ui (добавляются CLI shadcn)
  components/states/    # Состояния страниц
  components/form/      # Общие элементы форм TanStack Form
  assets/class-icons/   # Иконки классов (WebP 104 px, имя — slug класса)
  lib/supabase/         # Конфигурация, клиент, callApi, загрузки, toAppError
  lib/errors.ts         # AppError и единый каталог сообщений
  lib/storage.ts        # Единственный доступ к localStorage/sessionStorage
  lib/format-date.ts    # Единственное форматирование дат
  lib/utils.ts          # Объединение CSS-классов (cn)
  styles.css            # Токены, тема Tailwind 4 и базовые стили
stories/                # Storybook: история для каждого компонента ui/states
tests/                  # Vitest: клиент, проверки scripts/, tests/server/
e2e/                    # Проверки production build в Playwright
supabase/               # Конфигурация, миграции, функция api и общий код
scripts/                # TypeScript-скрипты проверок и сервисных команд
.github/workflows/      # CI и ручная публикация Pages
```

Доменные модули добавляются в `src/features/` вместе с задачами. Клиент
импортирует из серверного кода только контракты (`@contracts/*`). Функция
`api` работает в Deno-совместимом runtime и не входит в Vite-сборку; её
сервисы и HTTP-обработчик проверяет `npm run test:server`.

Границы модулей проверяются автоматически: supabase-js и клиент Supabase —
только в `src/lib/supabase/*.ts` и `src/features/auth/*.ts`, Kysely — только
в репозиториях и `_shared/db/`, браузерные хранилища — только через
`src/lib/storage.ts` (Oxlint, `.oxlintrc.json`); SQL вне репозиториев,
истории компонентов и единственность функции `api` —
`npm run check:architecture`.

Подробности backend: [supabase/README.md](supabase/README.md).
Правила разработки и принятые решения: [AGENTS.md](AGENTS.md).

## GitHub Pages и собственный домен

Удалённая публикация пока не выполнялась. После создания публичного
репозитория и подключения домена:

1. В Settings → Pages выбрать Source: **GitHub Actions**.
2. Проверить защищённую default branch и environment `github-pages`.
3. При подключении Supabase создать repository **Variables**
   `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Это публичные
   значения. Для статического каркаса можно оставить обе переменные пустыми.
4. Создать Variable `PAGES_CUSTOM_DOMAIN` с реальным доменным именем без
   протокола и пути. Workflow добавит `CNAME` в собранный артефакт.
5. Настроить домен в Pages, DNS и HTTPS согласно документации GitHub.
6. Запустить **Deploy GitHub Pages** вручную из default branch. Перед
   загрузкой `dist/` workflow повторит проверки и браузерные тесты.

Адрес домена пока не указан, поэтому фиктивного `CNAME` в проекте нет.
CI на push и pull request проверяет код, но не публикует сайт. В задаче
сборки только `contents: read`; права `pages: write` и `id-token: write`
получает отдельная задача публикации.

Маршрутизация использует `/#/…`: Pages всегда запрашивает существующий
HTML-файл, а маршрут обрабатывает браузер. `base: './'` позволяет работать
также по адресу `owner.github.io/repository/`. Чистые URL без `#` требуют
отдельного решения и сейчас не включены.

Для backend используем возможности Supabase Free. Лимиты и условия могут
меняться; перед реализацией новых функций проверять их соответствие тарифу.
Подключение платных возможностей и отдельного VPS не предусмотрено.

## Дизайн-система и Storybook

Визуальная основа повторяет основной прототип: угольные поверхности, золотые акценты, светлый текст и изображение на фоне. Токены темы и общие стили находятся в `src/styles.css`, компоненты — в `src/components/ui/`. Storybook обязателен: у каждого компонента `src/components/ui/` и `src/components/states/` есть история (`npm run storybook`); статическая сборка `npm run build-storybook` входит в `npm run check`. Примеры не подключены к данным и не реализуют продуктовые действия.

Текстовые поля используют нативные элементы, а список выбора — доступный компонент Radix; подпись передавайте через `Field`, а для таблиц сохраняйте заголовки и контейнер с горизонтальной прокруткой. Тему и компоненты расширяйте вместе с утверждёнными экранами; новый компонент shadcn/ui добавляется CLI shadcn и переоформляется токенами.
