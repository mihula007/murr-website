# Резервное копирование и восстановление

Инструкция администратору. Решение владельца: копии делаются вручную, по
его усмотрению, без обязательной периодичности и автоматизации. Supabase
Free автоматических копий не даёт: без своей свежей копии восстановление
не гарантируется.

Копия содержит личные данные участников (email, ники, переписку).
Хранить её только у себя (зашифрованный диск или архив с паролем), **не в
Git и не в публичных местах**. Папка копий должна быть вне репозитория.

Процедура ещё не проверялась восстановлением на этом проекте. Первую
копию стоит пробно восстановить в локальный стек (раздел «Пробное
восстановление»), а найденные расхождения записать сюда.

## Что входит в копию

| Часть                     | Как сохраняется                         | Без неё                                  |
| ------------------------- | --------------------------------------- | ---------------------------------------- |
| База: схема, данные, Auth | `supabase db dump` (три файла)          | потеря всех данных                       |
| Файлы Storage             | S3-доступ Storage или ручная выгрузка   | пропадут аватары и картинки              |
| Секреты и настройки       | не копируются: есть в Git и у владельца | восстанавливаются по [deploy](deploy.md) |

Пользователи Auth (`auth.users`, хеши паролей) входят в выгрузку данных,
поэтому после восстановления вход по прежним паролям работает. Значения
Vault не переносятся: они зашифрованы ключом проекта, их задают заново.

## Сделать копию базы

Нужны залогиненный и привязанный CLI (`deploy.md`, «Подготовка») и
Docker Desktop. Пароль БД, если CLI спросит, — из менеджера паролей.

Из папки репозитория (дату заменить на текущую):

```sh
mkdir -p ~/murr-backups/2026-11-14
npx supabase db dump --remote -f ~/murr-backups/2026-11-14/roles.sql --role-only
npx supabase db dump --remote -f ~/murr-backups/2026-11-14/schema.sql
npx supabase db dump --remote -f ~/murr-backups/2026-11-14/data.sql --use-copy --data-only -x "storage.buckets_vectors" -x "storage.vector_indexes" -x "vault.secrets"
```

Команды только читают облако.

## Сделать копию файлов Storage

Buckets `avatars` и `publication-images`. Способ — S3-доступ Storage:
Dashboard → Storage → S3 Configuration → создать ключ доступа, затем
любой S3-клиент (например `rclone` или `aws s3 sync`) с endpoint из той же
страницы. Ключ доступа — секрет: хранить в менеджере паролей, удалить в
Dashboard, если больше не нужен. Запасной способ для небольших объёмов —
скачать файлы в Dashboard → Storage вручную.

## Восстановление

Если проект жив, но данные испорчены, восстанавливать в **новый** проект
Free, проверить и только потом переключать сайт: старый проект остаётся
источником, пока новый не проверен.

1. Создать проект Free (eu-central-1), привязать CLI к нему.
2. Восстановить базу (нужен `psql`; строка подключения — Dashboard →
   Connect, секрет):

   ```sh
   psql --single-transaction --variable ON_ERROR_STOP=1 \
     --file roles.sql --file schema.sql \
     --command 'SET session_replication_role = replica' \
     --file data.sql --dbname "<строка подключения>"
   ```

   Ошибки прав `supabase_admin` или `cli_login_postgres` — закомментировать
   соответствующие строки по [документации Supabase](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).

3. Отметить миграции применёнными, чтобы `db push` не повторял их:
   `npx supabase migration repair --status applied <версия> --remote`
   для каждой версии из `supabase/migrations/`.
4. Buckets, функция, Secrets, Vault, `config push` — по [deploy](deploy.md),
   «Первичная настройка», шаги 3–9.
5. Загрузить файлы Storage в те же пути.
6. Сменить GitHub Variables `VITE_SUPABASE_URL` и
   `VITE_SUPABASE_PUBLISHABLE_KEY` на новый проект, выпустить клиент заново.
   Вебхук Telegram перенаправить командой `telegram:webhook`.

## Пробное восстановление

Проверка копии без облака — в локальный стек (данные локального стека
будут уничтожены):

```sh
npm run supabase:start
psql --single-transaction --variable ON_ERROR_STOP=1 \
  --command 'SET session_replication_role = replica' \
  --file data.sql --dbname postgresql://postgres:postgres@127.0.0.1:54322/postgres
```

Перед этим `npm run supabase:reset` создаёт схему из миграций; `data.sql`
ложится поверх неё. Миграции уже заполняют каталог классов и историю
миграций, поэтому возможны конфликты ключей: тогда очистить эти таблицы
перед загрузкой или восстанавливать с `schema.sql`, как в облаке, и
записать найденный способ сюда. Затем открыть сайт локально и проверить
вход и разделы. После проверки вернуть стек: `npm run supabase:reset`.

## Пауза проекта

Free ставит проект на паузу после недели без активности
([limits](supabase-free-limits.md)). Данные при паузе сохраняются, проект
возобновляется кнопкой **Resume project** в Dashboard в течение года.
Пауза — не замена копии.
