# Очереди наград КХ — план реализации

> **Для исполнителя:** выполнять по шагам в `main`; не создавать ветку или отдельную рабочую папку. Изменения реализации сохранить отдельным Conventional Commit после проверок.

**Цель:** добавить общую страницу КХ с 14 очередями наград, записью в конец, самостоятельным снятием и выдачей наград мастером.

**Устройство:** одна таблица хранит активные записи по очереди и аккаунту; её внешний ключ и смена роли удаляют записи, когда участник теряет доступ. Единственная Edge Function `api` отдаёт страницы сразу по всем очередям и проверяет каждое действие на сервере. Клиент показывает виртуализированную 14-колоночную сетку на широком экране и один раскрываемый список на телефоне.

**Стек:** TypeScript strict, React 19, TanStack Router/Query, существующий Radix Select для выбора одной очереди на телефоне, Tailwind CSS 4 по токенам темы, zod, TanStack Virtual через `src/components/virtual-list.tsx`, Supabase Postgres и существующая функция `api`.

**Спецификация:** [docs/requirements/25-kh-queue.md](../../requirements/25-kh-queue.md), требования KHQ-01–09.

## Общие ограничения

- Node.js 24; вся работа — в `main`.
- Клиент читает и меняет серверные данные только через `callApi` из `src/lib/supabase/api.ts` и существующую функцию `api`.
- Чтение выполняется через `useQuery`/`useInfiniteQuery`; запись — через `useMutation`.
- Схемы входных данных и общие константы размещаются в `_shared/contracts/`, используют zod и экспортируются через `@contracts/*`.
- Очереди поддерживают более 50 записей: курсор для каждой из 14 очередей, `useInfiniteQuery`, `VirtualList`; мобильный вид без прокрутки экрана вбок.
- Все стили используют токены темы; новые зависимости, серверы и секреты не добавляются.
- Новые данные для ручного просмотра добавляются в `scripts/seed-dev.ts`.
- Unit/component проверяются Vitest; сервер — `npm run test:server`; схема — `npm run supabase:test`; E2E добавляется, но запускается только при выкладке.

## Главные риски для проверки

1. Участник пытается записаться второй раз в ту же очередь или одновременно с двух вкладок — уникальность защищает запись, состояние интерфейса обновляется после ответа сервера.
2. Гость, кандидат, чтец, член, офицер или администратор пытается отметить выдачу — только мастер может удалить чужую активную запись как выданную.
3. Участник пытается снять чужую запись — операция удаляет только запись текущего аккаунта.
4. Смена роли лишает пользователя доступа — записи исчезают в той же транзакции, а активная очередь остаётся в порядке ID без пропусков/дубликатов.
5. Длинный ник, ошибка подгрузки, очередь длиннее 50 и ширина 375 px — текст и действия доступны, повтор загрузки работает, горизонтальной прокрутки нет.
