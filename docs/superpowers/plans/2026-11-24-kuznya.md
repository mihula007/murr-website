# Калькуляторы «Кузни» — план реализации

> **Для исполнителя:** выполнять последовательно внутри `main`; в проекте не создавать ветки или отдельные рабочие папки.

**Цель:** добавить доступную внутренним ролям категорию «Кузня» с семью адаптивными калькуляторами, ручными ценами и сохранением введённых значений на устройстве.

**Устройство:** единый каталог и чистые расчётные функции находятся в общем коде `shared/forge` и используются клиентом и единственной Edge Function. Крупные каталоги выдаются внутренним ролям курсорными страницами через `forge/catalog`; личные запасы, цены и прогресс остаются локальными и разделяются по ID аккаунта. Каждый калькулятор имеет отдельный маршрут в категории навигации «Кузня».

**Стек:** React 19, TypeScript strict, TanStack Router, TanStack Query, TanStack Virtual через `src/components/virtual-list.tsx`, zod, одна Supabase Edge Function `api`, Tailwind CSS 4 по токенам темы. Новые зависимости и таблицы не нужны.

**Требования:** [docs/requirements/24-forge.md](../../requirements/24-forge.md), HOM-22.

**Дополнение по решению сопровождающего от 24.11.2026:** категория «Кузня»
стоит перед «Управлением» и видна всем ролям. Все семь страниц и серверный
каталог доступны только администратору; остальные роли видят заглушку. При
ручной проверке входить администратором для калькуляторов, участником — для
проверки заглушки.

## Общие ограничения

- Работа ведётся только в `main`, Node.js 24.
- Клиентские запросы идут только через `callApi` в существующую функцию `api`.
- `useQuery`/`useInfiniteQuery` — чтение; все записи на сервере, если появятся, только через `useMutation`.
- Цены и пользовательские значения не передаются на сервер; запись в браузерное хранилище идёт только через `src/lib/storage.ts`.
- Все новые стили используют токены темы; неизвестные `VITE_*` и реальные секреты не добавлять.
- Полные каталоги «Эквип», «Мирозданки» и «Жребия» ищутся и подгружаются на сервере, отображаются виртуальным списком.

## Главные риски для проверки

1. Перепутанная привязка между грейдом, исходным предметом и рецептом — отдельные контрольные случаи каждого калькулятора в `tests/forge/calculations.test.ts`.
2. Округление и случайные величины меняют требуемое число ресурсов — тесты на границе `ceil`/`floor`, а вероятностный результат «Жребиев» сверяется с тройкой оценок исходного алгоритма.
3. Пустой, испорченный или отрицательный ввод не должен создавать `NaN`, отрицательную цену или ложный успех — тесты zod-схем и компонентов полей.
4. Поиск/фильтр длинного каталога не должен пропускать записи между страницами — тест стабильного курсора, одинаковые имена, смена фильтра и конец списка.
5. Переключение аккаунта на том же устройстве не должно показывать чужие цены или отметки — тест ключа локального сохранения на разных ID.

## Файловая карта

- `shared/forge/catalogs.ts` — статические данные предметов, рецептов, грейдов, титулов и вариантов ресурсов, общие для клиента и Edge Function.
- `shared/forge/calculations/*.ts` — чистые расчётные функции по семи инструментам и общие операции денег/ресурсов.
- `supabase/functions/_shared/contracts/forge.ts` — запрос и ответ каталога, схемы страниц и типы строки.
- `supabase/functions/_shared/forge/service.ts` — проверка внутренней роли, поиск, фильтр и keyset-страницы каталога.
- `supabase/functions/_shared/app.ts` — маршрут `forge/catalog`.
- `src/features/forge/` — страницы семи калькуляторов, общие числовые поля, список каталога, результаты, ключи запросов и сохранение введённых значений.
- `src/app/navigation.ts`, `src/app/shell/app-shell.tsx`, `src/routes/forge.tsx`, `src/app/router.ts` — категория, полная ширина, семь защищённых адресов.
- `vite.config.ts`, `tsconfig.app.json` — общий псевдоним `@forge/*` на `shared/forge/*`.
- `tests/forge/`, `tests/server/forge.test.ts`, `e2e/forge.spec.ts` — расчёты, интерфейс, API и пользовательские сценарии.
- `docs/architecture/module-decisions.md`, `docs/architecture/lists.md`, `docs/requirements/24-forge.md` — уже обновлены отдельным коммитом требований.

## Самопроверка плана

- Все семь страниц, формулы, сохранение, каталог и права имеют отдельные задачи и тесты.
- Схема данных не меняется, поэтому миграция и `seed-dev.ts` не нужны.
- План не меняет платформенные ограничения и не добавляет зависимости.
