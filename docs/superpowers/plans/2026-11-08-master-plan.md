## Сквозные правила (действуют на каждом этапе)

### Определение готовности этапа

1. Требования блока реализованы от интерфейса до базы; зависимость от ещё не сделанного блока явно записана в документе этапа.
2. `npm run check` проходит; для БД-этапов дополнительно проходят тесты доступа (см. ниже).
3. Для каждой роли проверены меню, чтение и **прямая** запрещённая операция (GEN-02): скрытая кнопка не считается защитой.
4. Затронутые экраны проверены на desktop и узком экране (Playwright, два проекта) и вручную в браузере.
5. Для каждого действия, меняющего состояние, зафиксировано решение «аудит / не аудит» в требованиях; аудит записывается в той же транзакции (ADM-11).
6. Статусы требований обновлены: не начато → реализовано → проверено → принято (README требований).
7. `AGENTS.md` и `.env.example` обновлены, если появились решения или переменные; секреты не попали в Git (`npm run security:check`).

### Правила для Supabase-слоя

- Новые таблицы — миграциями, в схеме, не открытой через Data API; GRANT браузерным ролям не выдаются, RLS включён без политик (запрет по умолчанию). В SQL — только схема и ограничения целостности (PK/FK, `UNIQUE`, `CHECK`, `ON DELETE`); функций, процедур, триггеров и политик с правилами нет.
- Все чтения и изменения прикладных данных — сервисы Edge Functions (`supabase/functions/_shared/<модуль>/service.ts`); SQL — только в репозиториях (`repository.ts`). Связанные изменения (смена статуса + аудит + уведомление) — одна транзакция Postgres, открытая сервисом и переданная репозиториям.
- Прямое подключение к БД обходит RLS: каждый метод сервиса сначала проверяет сессию, текущую роль из БД, владение и состояние объекта.
- Колонки, которые нельзя показывать (email, город, дата рождения, анкета), не попадают в ответ: сервис возвращает отдельный набор полей для каждого сценария.
- Роль хранится в `profiles.access_role`, не в Auth metadata. Клиент не пишет роль, статус решения и аудит; браузер обращается только к Auth и Edge Functions.
- Типы TypeScript генерируются из локальной схемы и хранятся в Git; `supabase db reset` + проверка миграций выполняются в каждом этапе с БД.
- Перед использованием возможности платформы (pg_cron, Realtime, Storage-лимиты) проверять актуальные квоты Free (ограничение AGENTS.md).

### Стратегия тестов доступа (вводится на этапе 3, расширяется дальше)

- **Тесты сервисов и Edge Functions** (Deno, на локальном Supabase) — матрица «роль × операция»: для каждого метода — разрешённые и запрещённые вызовы под ролями guest / applicant / reader / member / officer / admin, под своим и чужим объектом, напрямую по HTTP.
- **Проверка схемы** (`supabase test db`, pgTAP) — браузерные роли `anon`/`authenticated` не имеют доступа к прикладным таблицам; ограничения целостности работают.
- **Vitest + Testing Library** — клиентская логика и компоненты.
- **Playwright** — сценарии E2E-01…E2E-07 по мере появления, desktop + mobile.
- Тесты БД и Edge Functions запускаются в CI после появления первой миграции (Docker на GitHub runner бесплатен). Отдельный пункт этапа 3: убедиться, что локальный Supabase запускается на машине владельца (нужен Docker Desktop).

### Сквозные UI-обязательства

- Уход со страницы с несохранёнными изменениями — подтверждение (Q-17). Механизм создаётся на этапе 2 и подключается к каждой форме.
- Все формы: ошибки у полей, `htmlFor`, фокус виден, состояние загрузки/ошибки/пусто — из общих компонентов этапа 2.
- Ошибка сохранения никогда не показывается как успех (GEN-03); после мутации инвалидируются связанные запросы TanStack Query; кеш очищается при выходе и смене аккаунта.

> **Статус: завершён 08.11.2026** по [подробному плану](2026-11-08-stage-2-interface-navigation.md); проверка — [журнал](2026-11-08-stage-2-verification.md). **Требования:** HOM-01–03, HOM-12–13, HOM-14–15 (каркас), Q-17, раздел «Дизайн» в `AGENTS.md`.

## Этап 3. Аккаунт и доступ

> **Статус: завершён 08.11.2026** по [подробному плану](2026-11-08-stage-3-account-access.md); проверка — [журнал](2026-11-08-stage-3-verification.md). Отличия от плана перечислены в журнале.

**Цель.** Безопасная идентификация, сессия, роли на сервере, профиль, основа аудита, первый администратор.

**Требования:** ACC-01–15, ACL-01, 06–10 (серверная часть), ADM-06, ADM-10/11 (основа), Q-10, Q-11, Q-12, Q-15, Q-23, Q-24 (исключение первого админа).

### 3.0. Проектный подэтап (до кода) — самый рискованный

Регистрация не атомарна: Auth, Storage и Postgres — три разных хранилища. До миграций нужен короткий design-документ (`docs/architecture/registration-flow.md`) с решением по пунктам:

- **Где живут данные формы между отправкой и подтверждением кода.** Варианты: (а) в браузере (`sessionStorage`, аватар как Blob в памяти/IndexedDB) — просто, но теряется при закрытии вкладки; (б) в Supabase Auth `user_metadata` — анти-вариант (недоверенно, утечки в логи); (в) сначала создаём Auth-пользователя и приватную запись «незавершённая регистрация» со сроком жизни. **Предложение:** (в) без аватара-файла до подтверждения; после подтверждения — загрузка аватара в приватный bucket и вызов одной операции сервиса `completeRegistration` (Edge Function). Если пользователь закрыл вкладку, при входе он попадает на экран «Завершите регистрацию» и вводит недостающие поля повторно.
- **Идемпотентная `completeRegistration`:** проверяет, что email подтверждён и аватар лежит в его папке, создаёт `profiles(applicant)` + `join_applications` + аудит одной транзакцией; повторный вызов безопасен; уникальность активной заявки защищает от двух вкладок.
- **Одно или два события аудита** при регистрации + заявке (открытый пункт из обсуждения). **Предложение:** одно составное событие «регистрация и создание заявки».
- **Очистка временных файлов:** срок и механизм (Edge Function по расписанию или очистка при следующей попытке).
- **Письма:** на этапе разработки — локальный Mailpit; шаблон письма с кодом (OTP), не ссылкой — из-за hash-router (AGENTS.md: auto redirect отключён).
- **Восстановление пароля (ACC-11)** требует callback, совместимого с hash-router; либо тоже через OTP. **Предложение:** сброс пароля кодом из письма (`verifyOtp` типа recovery) — без redirect.
- **Первый администратор:** закрытая процедура. **Предложение:** однократная закрытая команда на TypeScript (тот же сервис аккаунтов), которую владелец запускает локально или через защищённый вызов Edge Function с секретом из Supabase Secrets; повторный запуск отклоняется, если админ уже есть; пишет аудит; не принимает ввод из публичного клиента.

### Состав работ после design-документа

1. **Миграции:** `character_classes` (справочник, ROS-09 — наполнение списком классов из прототипа, без «исправления» написаний), `profiles`, `join_applications` (минимально, чтобы заявка создавалась), `audit_log` с механизмом «последние 1000» (вытеснение в сервисе аудита в той же транзакции; тест на конкурентные вставки).
2. **Сервисы и репозитории:** основа `_shared` (подключение и транзакции, проверка сессии и роли, ошибки HTTP); владелец читает/пишет свой профиль (кроме `access_role`, `joined_on`); администратор читает профили; запись ролей из клиента невозможна; аудит читает только admin. Таблицы закрыты для Data API.
3. **Storage:** приватный bucket `avatars`, JPEG/PNG/WebP ≤ 500 KB (Q-11), серверная проверка типа и размера (лимит bucket + проверка в сервисе); загрузка по подписанной ссылке от Edge Function; сжатие клиентом до 512 px (ACC-08).
4. **Клиент Auth:** провайдер сессии, контекст доступа в роутере (`beforeLoad`), страницы: регистрация (мульти-шаговая форма, TanStack Form), ввод кода, вход, «Завершите регистрацию», выход (ACC-12), восстановление пароля, кабинет, редактирование профиля, смена пароля (ACC-09/10, доступно чтецу). Очистка кеша при выходе.
5. **Подключение навигации:** заглушка роли этапа 2 заменяется реальным контекстом; удаляется dev-переключатель; кнопка аккаунта в шапке.
6. **Аудит:** событие регистрации; сервис аудита `audit.write(tx, …)` — единая точка записи для всех следующих этапов (allowlist полей `details`, без паролей/токенов/текстов анкет).
7. **Тесты доступа:** первый набор тестов сервисов и Edge Functions (роль × операция для профиля, аудита, заявок) и pgTAP-проверка закрытости таблиц; Playwright: регистрация с кодом из Mailpit, прерывание и продолжение, вход/выход.
8. **CI:** добавить запуск локального Supabase, тесты Edge Functions и `supabase test db`.

## Этап 4. Заявки, членство и состав **[Изменение порядка]**

> **Статус: завершён 11.11.2026** по [подробному плану](2026-11-11-stage-4-applications-roster.md); проверка — [журнал](2026-11-11-stage-4-verification.md). Отличия от плана:
>
> - Блокировка и смена роли — одна операция `accounts/set-role`, восстановление — `accounts/restore-reader` (доступна офицеру). Назначение той же роли ничего не меняет и не пишет аудит.
> - Карточка состава содержит роль (для действия ROS-07), но не дату вступления; дата видна владельцу в кабинете и администратору в «Аккаунтах».
> - Сервер отдаёт статистику по всем классам справочника, включая нулевые; панель, как в прототипе, показывает только классы с участниками (17 чипов не помещались).
> - Новая заявка после отказа — `/#/account/application`: адреса под `/applications` закрыты для кандидата таблицей навигации.
> - TanStack Table — версия 9 (`useTable`); новых компонентов shadcn не потребовалось, добавлены общий `ConfirmActionDialog` и `ClassIcon`. Иконки классов из прототипа уменьшены до WebP 104 px (81 KB вместо 1,25 MB) без новых зависимостей.
> - После прямого решения путь кандидата помечает этапы голосования «Не потребовалось», а не «пройдено». Конфликт решения показывается в карточке постоянным уведомлением.
> - Любой ответ `forbidden` от `api` перечитывает `me` (общий `createQueryClient`).
> - E2E: рост численности проверяется как «не меньше +1» из-за параллельных сценариев CI; прямые запрещённые вызовы проверяются один раз (проект `chromium`). Сценарий регистрации этапа 3 обновлён под новый заголовок пути кандидата.

**Цель.** Внутренний доступ становится реальным: рассмотрение, приём/отказ, состав, блокировка и восстановление чтеца.

**[Изменение порядка]** В исходной таблице блокировка/восстановление чтеца и смена ролей отнесены на этап 11. Но E2E-06 и ACL-06 нужны уже тут: без них нельзя проверить «чтец = гость + профиль» и роль `reader` останется недостижимой. Поэтому на этап 4 переносятся: смена роли (admin), исключение/блокировка (admin), восстановление чтеца (officer/admin). На этап 11 остаются поиск/сортировка списка аккаунтов, просмотр аудита, смена пароля другого аккаунта и удаление пользователя.

2. **Миграции:** `publications`, `publication_attachments` (приватный bucket `publication-images`, ≤ 1 MB, JPEG/PNG/WebP — Q-11), `market_listings` (без файлов, ссылки допустимы), категории, флаги обсуждения, статусы черновик/опубликовано.
3. **Права в сервисах:** публикации — создают officer/admin, правит автор-офицер или admin, админ видит все черновики; рынок — member/officer создаёт и правит **свои**, админ — любые. Отдельные сервисы и проверки прав для публикаций и рынка (не переиспользовать права, граница из `02-page-map.md`).
4. **Экраны:** ленты и поиск (простой `ilike`/full-text — начать с простого, GIN по необходимости), редактор с предпросмотром, черновики, галерея вложений, подписи автора, снятие с публикации, подтверждение удаления, `useUnsavedChangesGuard`.
5. **Файлы:** загрузка с проверкой типа/размера (клиент + серверный bucket-лимит + проверка фактического типа в Edge Function при привязке), короткие signed URL, очистка осиротевших вложений при удалении публикации.
6. **Тесты:** тесты сервисов (черновик чужого не виден; офицер не правит чужую публикацию; член не создаёт публикацию; админ правит любую; рынок: чужое объявление недоступно); Vitest для санитайзера (набор XSS-векторов); Playwright E2E-04 и E2E-05.

### Решения до старта

- Выбор редактора и формата (см. п.1) — основное решение этапа.
- Нужны ли видео в галерее (PUB-15 упоминает «изображения/видео»)? Q-11 разрешает только изображения; видео — внешние ссылки? Уточнить.

### Готово когда

### Состав работ

4. **Обновление в реальном времени:** сначала — опрос TanStack Query с коротким интервалом только пока диалог открыт; Supabase Realtime подключать **только** после проверки лимитов Free по числу соединений. Q-20: набор функций не расширяется.

6. **Тесты:** тесты сервисов (доступ следует родителю во всех 4 случаях; нельзя писать в закрытое; нельзя править чужое/после 5 минут); Vitest для упоминаний и ответов; Playwright desktop/mobile.

### Решения до старта

- Приватность списка прочитавших (оставлено открытым). **Предложение:** виден только автору сообщения и офицерам/админам.

## Этап 10. Внутренние уведомления и главная

**Требования:** NTF-01–13, HOM-01 (колокольчик), HOM-04–09, HOM-11, ACT-12, 13, ROS-08.

> **Статус: реализован 13.11.2026** по [подробному плану](2026-11-13-stage-10-notifications-home.md); проверка — [журнал](2026-11-13-stage-10-verification.md). ### Состав работ

1. **Источники уведомлений** подключаются там, где их порождают сервер-операции этапов 4–9: решение по заявке (APP-14), добавление в группу/назначение лидером (GRP-17), упоминание и ответ (DSC-07), и др. по NTF-03. Этап проверяет, что каждый источник создаёт ровно одно уведомление (дедупликация `UNIQUE(recipient,source_kind,source_id,kind)`); действия над самим собой не уведомляют (NTF-04).
2. **Серверные счётчики разделов:** таблица «последний просмотр раздела» на пользователя; функция «сколько новых объектов с последнего просмотра» отдельно для ивентов, голосований, публикаций, объявлений (NTF-09–12); собственные объекты и начальное состояние учитываются по NTF-12.
3. **Экраны:** колокольчик (панель, история, непрочитанные, переход к источнику, недоступный/удалённый объект — понятное состояние NTF-07), красные счётчики в меню (слот готов с этапа 2).
4. **Главная:** реальные данные по ролям — HOM-04–09: путь кандидата по этапам заявки, численность, число актуальных событий и до трёх карточек, топ-5 месяца, краткий состав (только внутренние роли), переход к голосованиям; ответ на событие с главной использует те же данные (HOM-08); кнопка «Весь учёт» — officer/admin.
5. **Тесты:** тесты сервисов (получатель читает только свои; чужие отметки просмотра недоступны); Playwright: разные роли видят разную главную, счётчик уменьшается после открытия раздела.

### Решения до старта

- Срок хранения уведомлений и поведение ссылок на удалённый объект (открытый пункт схемы). **Предложение:** хранить без срока (NTF-08 снял лимит), но при росте — очистка старше N месяцев; ссылка на удалённый объект показывает «Объект удалён».
- Использовать ли Realtime для колокольчика (см. этап 9); начать с опроса раз в 30–60 с при видимой вкладке.

## Риски

1. **Регистрация (этап 3)** — самая сложная часть: три хранилища без общей транзакции. Лечится design-документом и идемпотентной операцией сервиса до написания UI.
2. **Удаление пользователя** (этап 11) пронизывает все таблицы. Лечится тем, что `ON DELETE` и обезличивание проектируются с первой миграции, а не переделываются в конце.
3. **Free-квоты** (письма Auth, Storage, Realtime, pg_cron): каждый этап с такой зависимостью начинается с проверки актуальных лимитов.
4. **Объём:** этапы 4, 7, 8 крупные; подробный план каждого дробится на задачи ≤ 1 дня с отдельным коммитом и проверкой.
5. **Безопасность колонок и прав:** прямое подключение Edge Functions обходит RLS — каждый «ограниченный» просмотр (заявка, ростер, голосование) и каждая операция покрываются тестом прямого вызова под каждой ролью.
