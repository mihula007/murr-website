# Характеристики персонажей и рейтинг силы — план реализации

> **Для исполнителя:** использовать `superpowers:executing-plans`; выполнять задачи по порядку, отмечать шаги чекбоксами. Разработка — только в `main`; рабочую папку и ветки не изолировать.

**Цель:** дать администратору возможность хранить пять характеристик персонажа, показывать их внутренним ролям в составе клана и сортировать состав по каждому показателю на главной.

**Архитектура:** необязательные значения характеристик и поле источника хранятся в профиле аккаунта. Существующие операции `accounts/card`, `accounts/*` и `roster/list` расширяются внутри функции `api`; источник остаётся администраторским. Главная использует общий кеш `roster/list`, а не отдельный серверный список.

**Стек:** TypeScript strict, React 19, TanStack Form/Query/Table, zod из `supabase/functions/_shared/contracts`, одна Edge Function `api`, Postgres через Kysely в репозиториях, Vitest, pgTAP и Playwright.

**Решение:** [характеристики персонажей и рейтинг силы](../specs/2026-11-14-character-strength-design.md).

## Общие ограничения

- Node.js 24 LTS и npm; установка — `npm clean-install` по `package-lock.json`.
- UI — React 19, Radix и shadcn/ui; стили — Tailwind CSS 4 только через токены темы.
- Формы — TanStack Form + zod; изменённые данные сохраняются через `useMutation`, кеш обновляется в `onSuccess`.
- Таблица рейтинга — TanStack Table v9 (`useTable`); на узком экране строки отображаются карточками без горизонтальной прокрутки.
- Новые необязательные поля не ломают текущий контракт. Миграции только вперёд; выкладка совместима: сначала миграция и функция, затем клиент.
- Backend остаётся одной Edge Function `api`; SQL — только в репозиториях через Kysely.
- Доступ к карточке и записи — серверная проверка `admin`; `roster/list` отдаёт показатели только ролям `member`, `officer`, `admin` и никогда не отдаёт им источник.
- Состав загружается целиком по Q-48 (до 200 участников; страховочный предел API 250, с `truncated`). Фильтр и сортировка рейтинга выполняются в браузере.
- Не добавлять зависимости или платные сервисы. Каждый вызов API расходует квоту Supabase Free.
- Секреты остаются вне исходников, тестовых данных и журналов.

## Особое внимание при проверке

1. `125,5к`, `125.5к`, пустая строка, недопустимый текст и переполнение: нормализация, отказ без изменения прежнего значения и отображение ошибки (контракт и серверные тесты, задачи 2–3).
2. Источник не должен попадать в ответы состава и главной даже для внутренней роли (серверные тесты, задача 2).
3. Гость, кандидат и чтец не должны получать характеристики через прямой вызов закрытой операции (серверные и e2e тесты, задачи 2 и 5).
4. Пустые показатели отображаются тире и сортируются после заполненных; одинаковые значения упорядочены по нику (модульные и компонентные тесты, задача 4).
5. Сбой записи не должен менять сохранённое значение; после повтора успешная запись отражается в карточке и рейтинге и появляется в аудите (серверный и e2e тесты, задачи 2–3 и 5).

## Task 2. Общий контракт и операции сервера

**Файлы:** создать `supabase/functions/_shared/contracts/character-stats.ts`; изменить `supabase/functions/_shared/contracts/accounts.ts`, `supabase/functions/_shared/contracts/roster.ts`, `supabase/functions/_shared/accounts/service.ts`, `supabase/functions/_shared/accounts/repository.ts`, `supabase/functions/_shared/roster/service.ts`, `supabase/functions/_shared/roster/repository.ts`, `supabase/functions/_shared/app.ts`; проверить в `tests/server/admin.test.ts`, `tests/server/roster.test.ts` или отдельном `tests/server/character-stats.test.ts`.

**Интерфейсы:** `setCharacterStat(deps: AppDeps, actor: Actor, body: unknown)` принимает `{ userId, field, value }`; `field` — `source | pa | pz | bu | hp | bd`. Числовой ввод сохраняется числом после проверки, пустой — как `null`; источник — строка или `null`. `accounts/get` добавляет необязательные поля статистики. `RosterMember` добавляет необязательные `pa`, `pz`, `bu`, `hp`, `bd` типа `number | null`.

- [ ] **Шаг 1: написать падающие серверные тесты.** Администратор читает и меняет каждое поле; каждое изменение обновляет профиль и создаёт одну запись аудита с исполнителем, целью и названием поля. Повтор того же значения не создаёт лишнюю запись. Проверить десятичную запятую/точку, суффикс `к`, пустое значение, неверный текст, отрицательное значение, более трёх дробных знаков и переполнение.
- [ ] **Шаг 2: проверить права и проекцию состава.** Не-администратор не меняет поле; гость, кандидат и чтец отклоняются. Внутренние роли получают пять чисел через `roster/list`, поле `character_stats_source` отсутствует в ответе. Администраторская карточка содержит источник и пять чисел.
- [ ] **Шаг 3: запустить серверные тесты до реализации.** `npm run test:server`; новые проверки падают на отсутствующей операции/полях, прежние проверки остаются зелёными.
- [ ] **Шаг 4: реализовать контракт, маршрут, сервис и репозиторий.** Добавить `accounts/set-character-stat`. Сервис требует роль `admin`, отклоняет цель с незавершённым удалением (`state_conflict`), проверяет цель и сохраняет одно поле с одной записью категории `profiles` в общей транзакции. Повтор прежнего значения не создаёт аудит. Не создавать уведомление. Серверный список отдаёт только пять показателей текущего состава.
- [ ] **Шаг 5: проверить контракт и сервер.** `npm run test:server`; все тесты проходят, а прямые вызовы с недостаточной ролью не возвращают данные и не меняют записи.
