# Этап 13. Telegram: привязка и анонсы — план реализации

> **Для исполнителя:** используйте superpowers:executing-plans, задачи выполняются по порядку; шаги отмечаются чекбоксами. Это подробный план этапа 13 из [мастер-плана](2026-11-08-master-plan.md). **Статус: проект, ждёт согласования владельцем.** Решения до старта — Q-76–Q-96 (14.11.2026). Этап выполняется до этапа 12 (запуск), который затем включает настройку рабочего бота.

**Цель:** член, офицер и администратор привязывают Telegram в кабинете; офицер и администратор отправляют из «Рассылки» анонсы в Telegram — анонс события с кнопками «Приду», «Не приду», «50/50» и «Изменить решение», отдельный анонс — только текстом; ответ кнопкой равен ответу на сайте, ответ на сайте обновляет сообщение.

**Архитектура.** Как на этапах 3–11: обработчик функции `api` → сервисы `telegram`, `broadcasts`, `events` → репозитории (Kysely). Вебхук Telegram — маршрут той же функции `api`, проверка — секретным заголовком. Bot API — через `fetch` без библиотеки бота (лёгкий старт функции). Новых Edge Functions нет. Новые переменные окружения — `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_BOT_USERNAME`, `SITE_URL`, `TELEGRAM_API_BASE` (тесты); `TELEGRAM_BOT_TOKEN` уже есть в шаблоне. Новая npm-зависимость — `cloudflared` (devDependencies, Q-95). Клиент — новый модуль `src/features/telegram/`, изменённые `src/features/broadcast/` и `src/features/account/`. Подробности — [технический проект](../../architecture/telegram-integration.md).

**Требования:** TGM-01–26, BRC-01, BRC-05, BRC-07, BRC-08/09 (отмена), BRC-13, EVT-04, EVT-05, Q-22, Q-43, Q-45, Q-76–Q-96; приёмка TGM 1–9, E2E-08. Не входят: ВКонтакте и MAX, другие доставки в Telegram (Q-86), регистрация рабочего бота и вебхука облака (этап 12).

## Решения владельца (14.11.2026)

- **Q-76.** «Изменить решение» как на сайте: показывает три кнопки, ответ не меняется до нового выбора; подписи — «Приду», «Не приду», «50/50».
- **Q-77.** Ответ на сайте обновляет активное сообщение события в Telegram.
- **Q-78.** Новый анонс того же события снимает с прежнего сообщения кнопки и строку ответа.
- **Q-79.** Изменение события не меняет отправленных сообщений; офицер отправляет новый анонс.
- **Q-80.** Текст редактируется только до отправки; истории анонсов на сайте нет.
- **Q-81.** Отправляют офицеры и администраторы.
- **Q-82.** Отправка — на странице «Рассылка»; черновики и шаблоны остаются; ВКонтакте и MAX недоступны; вложения убираются полностью.
- **Q-83.** Получатели — на момент отправки; «Отвязать» в кабинете; заблокировавший бота помечается неактивным.
- **Q-84.** После отправки — только toast, без статусов доставки.
- **Q-85.** Одна запись аудита на отправку.
- **Q-86.** Привязка и анонсы — весь объём Telegram.
- **Q-87, Q-95.** Локально — отдельный бот и туннель `cloudflared`.
- **Q-88.** Привязка — член, офицер, администратор; при переходе в чтецы связь хранится, но не используется.
- **Q-89.** Код привязки одноразовый, 15 минут; один Telegram ↔ один аккаунт.
- **Q-90.** Формат: тема жирным, затем текст; ответы бота на прочие сообщения; пояснение «бот остановлен» в кабинете.
- **Q-91.** Текст анонса, черновика и шаблона ≤ 3800 символов.
- **Q-92.** Отказ без получателей и для закрытого или начавшегося события.
- **Q-93.** После начала события кнопки снимаются только при нажатии.
- **Q-94.** Привязка и отвязка не пишутся в аудит.

## Решения исполнителя (можно оспорить при согласовании)

### Сервер

- **Шлюз Bot API** (`telegram/gateway.ts`): `sendMessage`, `editMessageText`, `editMessageReplyMarkup`, `answerCallbackQuery`, `setWebhook`, `deleteWebhook`. Результат — размеченный тип `ok | blocked | not_modified | gone | failed`, исключения наружу не выходят. 429 — одна пауза на `retry_after` (не дольше 5 с) и повтор. URL с токеном и тело ответа с токеном в лог не попадают: логируются метод и код ошибки Telegram. Таймаут запроса — 10 с.
- **`deps.telegram: TelegramGateway | null`.** Без `TELEGRAM_BOT_TOKEN` — `null`: `telegram/link-start`, `broadcasts/recipients`, `broadcasts/send` отвечают `telegram_unavailable` (503), `telegram/status` — `{ configured: false }`, вебхук — 404.
- **`deps.background(task)`** — фоновая задача после ответа. В `api/index.ts` — `EdgeRuntime.waitUntil`, в тестах Node — сбор обещаний, которые тест дожидается (`support.ts`). Общий код глобалов Deno не использует.
- **Общий ответ на событие.** Тело `respondToEvent` выносится в `saveAnswer(deps, viewer, eventId, answer)`; сайт и кнопка вызывают его, поэтому Q-43, роли и блокировка `FOR SHARE` одни. После коммита `events/respond` ставит `deps.background(syncEventMessage(...))` (TGM-21).
- **Код привязки** — 32 случайных байта в base64url (43 символа, допустимо для `start`), в БД — SHA-256 hex. `link-start` заменяет прежний код пользователя (`UNIQUE user_id`, upsert). Вебхук `/start <код>` в одной транзакции: блокирует строку кода `FOR UPDATE`, проверяет срок, удаляет код, upsert связи по `user_id`; чужой `telegram_user_id` ловит `UNIQUE` → ответ бота «Этот Telegram уже привязан к другому аккаунту», связь не меняется (TGM-04).
- **Вебхук.** Сверка `X-Telegram-Bot-Api-Secret-Token` за постоянное время; неверный — 404 (не раскрываем маршрут). Апдейт разбирается zod-схемой подмножества (`message.text`, `message.from`, `message.chat.type = private`, `callback_query`); прочее — 200 без действий. Сообщения не из личного чата игнорируются. Любая внутренняя ошибка после проверки секрета — лог и 200, чтобы Telegram не повторял апдейт. Username и имя связи обновляются при каждом апдейте от привязанного пользователя (TGM-05), `blocked_at` снимается при любом его сообщении (TGM-08).
- **Отправка.** Порядок — по [проекту](../../architecture/telegram-integration.md), раздел «Отправка анонса»: проверки → получатели → строка анонса события → пул до 20 запросов, темп ≤ 25 сообщений в секунду → на каждого успешного получателя короткая транзакция замены активного сообщения → перерисовка прежнего сообщения без кнопок → `blocked_at` для 403 → одна запись аудита `broadcasts/sent` (категория `broadcasts`). Сетевые вызовы — вне транзакций. Получатели — внутренние роли с `blocked_at is null`; число получателей кнопки подтверждения и отправки считает один запрос репозитория.
- **Повторная отправка.** Сервер не защищает от двойной отправки одного текста: подтверждение и блокировка кнопки на время запроса (Q-96).
- **Нажатие кнопки.** `callback_data`: `a:<eventId>:<y|m|n>` и `c:<eventId>`. Проверки по порядку: связь по `from.id` → активное сообщение `(eventId, userId)` совпадает с `chat_id` и `message_id` → `loadActor` → `saveAnswer` (для `a:`) или проверка роли и состояния события (для `c:`). Тексты отказов — каталог `telegram/messages.ts`. Отказ снимает кнопки сообщения; `forbidden` по роли — тоже (TGM-10). Всегда `answerCallbackQuery`.
- **Ошибки.** Новый код `telegram_unavailable` (503) в `contracts/errors.ts` и сообщение в `src/lib/errors.ts`. Отказы отправки — `state_conflict` с `reason`: `no_recipients`, `started`, `closed` (Q-92).

### Клиент

- **Кабинет** — карточка `TelegramLinkCard` из `src/features/telegram/` под профилем, только для внутренних ролей. Состояния: не подключён на сервере (пояснение, без кнопок) → не привязан («Привязать Telegram») → ссылка готова (кнопка-ссылка «Открыть бота» `<a target="_blank" rel="noopener">`, подсказка «нажмите «Запустить» в Telegram», «Получить новую ссылку») → привязан (@username или имя, «Отвязать» через `ConfirmActionDialog`) → бот остановлен (пояснение). `telegram/status` с `refetchOnWindowFocus: true`, запись — `useMutation`, кеш — в `onSuccess`.
- **Рассылка.** Убираются поле файлов, `files.ts`, проверки и тексты BRC-08/09. Каналы: Telegram выбран; ВКонтакте и MAX — недоступные флажки «не подключено». Плашка связанного события для `source.kind === 'event'` с «Снять связь» (существующий `clearSource`): «Анонс события: придёт с кнопками ответа». Кнопка «Отправить в Telegram» доступна при валидной форме и выбранном Telegram: `broadcasts/recipients` → `ConfirmActionDialog` «Отправить N получателям?» → `broadcasts/send` → toast «Отправлено в Telegram: N» (неудачи — «, не доставлено: M») → форма очищается без вопроса о несохранённых изменениях (`ignoreBlocker`). Счётчик символов и лимит 3800 — общая схема.
- **Сброс кеша.** Отправка не меняет данных сайта; кеш не сбрасывается. `events/respond` клиента не меняется.

### Локальная разработка

- `npm run telegram:dev` (`scripts/telegram-dev.ts`): быстрый туннель `cloudflared` к `127.0.0.1:54321` → `setWebhook` (`/functions/v1/api/telegram/webhook`, `secret_token`, `allowed_updates: ["message", "callback_query"]`, `drop_pending_updates: true`) → печать адреса без токена → по Ctrl+C `deleteWebhook` и остановка туннеля. Переменные — из `.env` (`node --env-file-if-exists=.env`).
- `npm run telegram:webhook -- --url <адрес функции>` — однократная регистрация вебхука облака (этап 12).
- README: создание тестового бота в BotFather, какие переменные заполнить, запуск `supabase:functions` + `telegram:dev`.

## Результаты задачи 0 (14.11.2026)

- **Supabase Free:** запрос функции — до 150 с (idle timeout и wall clock), CPU — 2 с на запрос без учёта ожидания ввода-вывода, память — 256 МБ, 500 000 вызовов в месяц; проект Free засыпает после недели без активности. Отправка 200 сообщений при 25 в секунду — около 8 с ожидания сети и мало CPU (JSON и `fetch`): укладывается с большим запасом, разбиение не нужно. Нажатия и привязки — доли процента месячной квоты.
- **Telegram:** без платных рассылок — около 30 сообщений в секунду на бота, не больше 1 в секунду в один чат, при превышении — 429. `secret_token` вебхука — 1–256 символов `A-Za-z0-9_-`, заголовок `X-Telegram-Bot-Api-Secret-Token`; любой ответ кроме 2xx Telegram повторяет. Текст сообщения — 1–4096 символов после разбора разметки; `callback_data` — 1–64 байта; текст `answerCallbackQuery` — до 200 символов; параметр `start` — до 64 символов `A-Za-z0-9_-` (рекомендован base64url). Ограничение правки в 48 часов относится только к бизнес-сообщениям, сообщения бота в личном чате правятся без срока. В HTML экранируются только `<`, `>`, `&`.
- **Маршрут вебхука:** `POST /functions/v1/api/telegram/webhook` без JWT доходит до обработчика `api` (ответ `{"error":"not_found"}` от него, а не от шлюза).
- **Фальшивый Bot API:** контейнер функций достигает сервера на машине владельца по `host.docker.internal`, даже если сервер слушает только `127.0.0.1`.
- **Фоновые задачи локально:** по документации Supabase локальный исполнитель по умолчанию завершает экземпляр сразу после ответа, и задача `EdgeRuntime.waitUntil` не доделывается; нужен `[edge_runtime] policy = "per_worker"` в `supabase/config.toml`. Цена — без горячей перезагрузки: после правки кода функции `supabase functions serve` перезапускается.
- **`cloudflared`:** npm-пакет `cloudflared@0.7.3` (обёртка JacobLinCool, 53 КБ) скачивает официальный бинарник с `github.com/cloudflare/cloudflared/releases`, по умолчанию последний. npm 12 проекта по умолчанию не запускает install-скрипты зависимостей, поэтому postinstall пакета не сработает — и не нужен. Быстрый туннель без аккаунта проверен: соединение за 8 с, POST дошёл до локального сервера. Новый адрес `*.trycloudflare.com` первые минуты не разрешается локальным DNS macOS (кеш отрицательного ответа) — на Telegram это не влияет, для ручной проверки нужен `curl --resolve` или ожидание.

## Отличия при реализации

- **`policy = "per_worker"`** в `[edge_runtime]` (результат задачи 0), иначе фоновое обновление сообщения после ответа на сайте (TGM-21) не выполняется локально и в e2e. README: после правки функции перезапустить `supabase functions serve`.
- **Бинарник `cloudflared` закреплён версией** `2026.10.7` (выпуск 30.10.2026): `scripts/telegram-dev.ts` при первом запуске сам ставит её функцией `install` пакета в `node_modules/.cache`, а не через postinstall. `allowScripts` в `package.json` не добавляется, CI бинарник не скачивает.
- **Вложения убраны целиком в задаче 1**, а не в задаче 5: удаление столбца ломало репозиторий черновиков, поэтому вместе со схемой убраны контракт, сервис, поле файлов на странице, `files.ts` и их тесты. Остальные правки «Рассылки» — в задаче 5.
- **Миграция применена `supabase migration up`**, а не `supabase:reset`: локальные данные владельца сохранены. В локальном стеке не было bucket `publication-images` из `config.toml` (стек старше этапа 8), из-за чего падал тест удаления пользователя; создан `supabase seed buckets` без сброса данных.
- **Анонс хранит тему и текст, а не HTML** (задача 2): экранирование `&` → `&amp;` удлиняет HTML, и допустимый текст в 3800 символов мог не пройти `CHECK` в 4096. HTML строится при отправке и перерисовке. Миграция ещё нигде не выложена, поэтому исправлена на месте; локальная БД изменена тем же `ALTER`.
- **Шаблон токена бота в сканере уже был** (`scripts/secret-rules.ts`, тест в `tests/check-secrets.test.ts`) — задача 2 его не меняла.
- **Сетевые ошибки шлюза логируются только типом**: в Deno текст ошибки `fetch` содержит адрес с токеном; тест проверяет, что токен не попадает в лог.
- **Telegram включается тремя переменными**: без любой из `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET` — `deps.telegram = null`. Тексты бота — простой текст, анонсы — HTML.
- **Код привязки забирается `DELETE … RETURNING`** (задача 3), а не блокировкой `FOR UPDATE`: одновременные `/start` с одним кодом получат его только один раз. Гонку двух аккаунтов за один Telegram ловит `UNIQUE telegram_user_id` — второй получает «уже привязан».
- **Нажатия кнопок до задачи 4** только закрывают индикатор (`answerCallbackQuery`).
- **Получатели не обрезаются порогом `MEMBER_LIST_LIMIT`** (задача 4): список наружу не отдаётся, а молча пропустить часть получателей нельзя. Аккаунты с незавершённым удалением (Q-74) получателями не считаются.
- **Модуль `telegram/announcements.ts`**: доставка анонса, синхронизация ответа с сайта и перерисовка сообщения; `events/service.ts` импортирует только его, поэтому циклических импортов нет. Фоновая задача — `_shared/background.ts` (`runInBackground`): ошибка только логируется.
- **Порядок проверок нажатия:** связь → событие существует → активное сообщение совпадает → роль → закрыто → началось. Удалённое событие отвечает «Событие удалено», хотя его активные сообщения уже удалены каскадом.
- **Аудит отправки** — действие `broadcast_sent`, категория `broadcast`; в `details` добавлены ключи `recipients`, `sent`, `failed`.
- **Фоновая задача в настоящей функции** (`EdgeRuntime.waitUntil` при `per_worker`) пока проверена только тестами Node: запущенный `functions serve` принадлежит другой сессии и не перезапускался. Проверка — в e2e задачи 7.
- **Отправка идёт через `form.handleSubmit`** (задача 5) с флагом намерения «черновик / отправка»: одна проверка и показ ошибок полей для обеих кнопок. Число получателей — `queryClient.fetchQuery` (разовая проверка), при нуле — пояснение без диалога.
- **`ConfirmActionDialog` получил необязательный `errorText`**: отказ отправки показывает причину (`no_recipients`, `started`, `closed`), а не общий текст конфликта.
- **Текст заполнения из события** (BRC-02) теперь говорит «Ответьте кнопками под сообщением или на сайте…» — анонс события приходит с кнопками.
- **Проверка в браузере** (375 и 1240 px, локальные тестовые аккаунты офицера и члена): блок Telegram в кабинете — привязан, отвязка с подтверждением, ссылка на бота; «Рассылка» — недоступные ВКонтакте и MAX, ошибки полей при отправке пустой формы, «Отправить некому», плашка анонса события, подтверждение с числом получателей. Горизонтальной прокрутки нет. Настоящая отправка — в задаче 6.
- **`functions serve` перезапущен этой сессией** (прежний процесс другой сессии остановился): теперь с `policy = "per_worker"`.
- **Живая проверка 14.11.2026** (задача 6, тестовый бот владельца, телефон владельца, локальный аккаунт офицера): привязка через ссылку из кабинета; отдельный анонс пришёл текстом, `<b>`, `&`, `>` показаны как текст; анонс события пришёл с тремя кнопками; «Приду» в Telegram сохранился на сайте; «Не приду» на сайте обновил сообщение в Telegram (фоновая задача при `per_worker` в настоящей функции); «Изменить решение» вернул три кнопки без смены ответа; повторный анонс того же события оставил первое сообщение текстом без кнопок и строки ответа, новое пришло со строкой ответа и «Изменить решение». В аудите — по записи на отправку.
- **`install`-скрипт `cloudflared` не нужен**: `npm install --ignore-scripts`, бинарник закреплённой версии скачивается `telegram:dev` при первом запуске. ESLint-правило хуков в Oxlint принимает функцию пакета `use` за хук React, поэтому она импортирована как `selectBinary`.
- **`npm run test:server` очищает прикладные таблицы локальной БД** (`resetAppData`, так было и до этапа): тестовые профили для ручной проверки пришлось создать заново.
- **Проверка на локальной функции:** без секрета и с неверным — 404, с верным — 200 `{}`, `telegram/status` гостя — 401.

## Списки этапа

Новых списков нет: `broadcasts/recipients` возвращает число, а не массив; получатели внутри `broadcasts/send` — участники клана (исключение Q-48, порог `MEMBER_LIST_LIMIT`). Реестр [списков](../../architecture/lists.md) не меняется.
