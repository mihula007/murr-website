# Регистрация, вход и восстановление доступа

Дата: 08.11.2026. Статус: **проект этапа 3, решения владельца Q-26–Q-34 учтены**; детали реализации — в [плане этапа 3](../superpowers/plans/2026-11-08-stage-3-account-access.md). Требования: ACC-01–15, Q-10, Q-11, Q-15, Q-21, Q-24.

## Исходные условия

- Три хранилища без общей транзакции: Supabase Auth (аккаунт, пароль, код), Storage (аватар), Postgres (профиль, заявка, аудит).
- Вся бизнес-логика — TypeScript в Edge Functions, SQL только в репозиториях (Q-26). Браузер обращается к Supabase Auth и к Edge Functions, но не к таблицам и не к Storage напрямую (кроме загрузки по подписанной ссылке, выданной функцией).
- Hash-router на GitHub Pages: письма содержат **шестизначный код**, а не ссылку; автоматическая обработка Auth redirect остаётся выключенной.
- Ник: до 9 символов, уникален с учётом регистра, может меняться (Q-27).

## Состояния аккаунта

| Состояние                               | Где видно                                                   | Что доступно                                              |
| --------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------- |
| Гость                                   | Нет сессии                                                  | Публичная главная, вход, регистрация, сброс пароля        |
| Не подтверждён                          | Есть пользователь Auth без `email_confirmed_at`, сессии нет | Ввод кода, повторная отправка кода                        |
| Незавершённая регистрация               | Сессия есть, профиля в `app.profiles` нет                   | Только экран «Завершите регистрацию» и выход; права гостя |
| Кандидат / чтец / член / офицер / админ | Профиль есть, роль — `profiles.access_role`                 | По матрице ACL                                            |

Незавершённую регистрацию отдельной таблицей не храним: её признак — пользователь Auth без профиля (Q-28). Персональных данных анкеты на сервере до подтверждения email нет.

## Основной сценарий

1. **Форма.** Гость открывает «Вступить в клан» и заполняет все поля Q-15: email, пароль (≥ 8), аватар, имя (≤ 12), ник (≤ 9), город, дату рождения, класс, рассказ о себе, до 10 ссылок на скриншоты снаряжения. Клиент проверяет поля той же zod-схемой, что и сервер; аватар уменьшается до 512 px по большей стороне без увеличения и проверяется на ≤ 500 KB.
2. **Проверка ника (подсказка).** Анонимный вызов `account/check-nickname` сообщает, свободен ли ник. Ник не резервируется — окончательная проверка в шаге 6.
3. **Аккаунт Auth.** `supabase.auth.signUp({ email, password })`. Поля анкеты (без пароля) записываются в `sessionStorage` вкладки, аватар хранится в памяти. Если Auth вернул пользователя без identities — email уже зарегистрирован: показываем «Аккаунт уже существует — войдите» и переводим на вход с подставленным email (ACC-01, приёмка 2).
4. **Код.** Письмо содержит `{{ .Token }}`. Пользователь вводит код: `verifyOtp({ email, token, type: 'signup' })` → сессия. Повторная отправка — `auth.resend({ type: 'signup', email })` с таймером на клиенте.
5. **Аватар.** `account/avatar-upload` проверяет сессию и выдаёт подписанную ссылку на загрузку в приватный bucket `avatars` по пути `<uid>/<случайный id>.<ext>`. Клиент загружает файл. Bucket сам ограничивает размер (500 KB) и MIME-типы.
6. **Завершение.** `account/complete-registration` с полями анкеты и путём аватара. Сервис в одной транзакции:
   - проверяет, что email подтверждён (`auth.users.email_confirmed_at`), и повторно валидирует поля;
   - если у пользователя уже есть профиль — возвращает его текущее состояние без изменений (идемпотентность, две вкладки);
   - проверяет, что объект аватара существует в папке пользователя, его размер ≤ 500 KB и сигнатура файла — JPEG/PNG/WebP;
   - создаёт `profiles` (роль `applicant`), `join_applications` (`pending_officer_review`), ссылки снаряжения;
   - пишет одно событие аудита «Регистрация и создание заявки» (Q-29);
   - после фиксации удаляет из папки `<uid>/` другие объекты, кроме сохранённого аватара (повторные загрузки не копятся).
     Уникальные ограничения (`profiles.id`, `game_nickname`, одна активная заявка) защищают от гонок: при конфликте ника возвращается ошибка `nickname_taken`, при конфликте профиля — повторное чтение и успешный ответ.
7. **Успех.** Только после ответа сервера клиент очищает `sessionStorage`, инвалидирует запросы и переходит на главную (Q-21) с сообщением «Заявка отправлена».

## Прерывания и сбои

| Где прервалось                                 | Что остаётся                                    | Как продолжить                                                                                                                   |
| ---------------------------------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| До `signUp`                                    | Ничего                                          | Заполнить форму заново (черновик в `sessionStorage` той же вкладки подставляется)                                                |
| После `signUp`, до кода                        | Неподтверждённый пользователь Auth              | Вход с паролем даёт `email_not_confirmed` → экран кода с повторной отправкой; повторный `signUp` тоже отправляет код             |
| После кода, до загрузки аватара или завершения | Сессия, пользователь без профиля, возможно файл | При любом входе состояние «незавершённая регистрация» → экран «Завершите регистрацию»; поля из вкладки или заново, аватар заново |
| Ошибка сети на завершении                      | Неизвестно, зафиксировано ли                    | Повтор того же вызова безопасен: сервис вернёт уже созданную заявку                                                              |
| Ник занят к моменту завершения                 | Сессия без профиля                              | Ошибка у поля ника на экране завершения, остальные поля сохранены                                                                |
| Истёк код                                      | Неподтверждённый пользователь                   | «Отправить код ещё раз»                                                                                                          |

Незавершённая операция никогда не показывается как успех (ACC-03, GEN-03). Неподтверждённые пользователи Auth без профиля не дают прав и не содержат анкеты; их очистка — административная задача этапа 11, расписание не нужно.

## Вход и выход

- Вход — `signInWithPassword`. Неверный email или пароль — общее сообщение «Неверный email или пароль»; новый аккаунт не создаётся (ACC-04). `email_not_confirmed` → экран кода.
- После входа клиент вызывает `account/me`: состояние (`incomplete` или профиль), роль, статус заявки, подписанная ссылка на аватар. Роль для меню и `RouteGate` берётся только отсюда; dev-переключатель ролей удаляется.
- Выход — `signOut()`, очистка кеша TanStack Query, переход на публичную главную (ACC-12). Смена пользователя в сессии тоже очищает кеш.

## Восстановление пароля (Q-30)

1. «Забыли пароль?» → email → `resetPasswordForEmail(email)`; ответ одинаковый для существующего и неизвестного адреса.
2. Письмо с кодом (`{{ .Token }}`, шаблон recovery). На той же странице пользователь вводит код и новый пароль дважды.
3. `verifyOtp({ email, token, type: 'recovery' })` → сессия → `updateUser({ password })` → переход в кабинет с сообщением «Пароль изменён». В аудит не пишется (Q-34).

## Смена пароля в кабинете (ACC-09, ACC-10)

Текущий пароль проверяется повторным `signInWithPassword` для email сессии; затем `updateUser({ password })`. Ошибки у полей: неверный текущий, короче 8, повтор не совпадает. Успех очищает поля и сворачивает форму. Чтец может менять пароль. Аудита нет (Q-34).

## Профиль и аватар

- `account/update-profile`: имя, ник, город, дата рождения, класс, рассказ; email не меняется (ACC-06). Ник проверяется на занятость с учётом регистра; прежний ник освобождается сразу (Q-27). Аудит — одно событие с перечнем изменённых полей без значений (Q-34).
- Аватар можно заменить (новая загрузка + путь в запросе) или убрать (Q-31). Старый файл удаляется после фиксации транзакции; неудачное удаление оставляет «осиротевший» файл в папке пользователя, его уберёт следующая замена.
- Чтение аватара — подписанная ссылка на 1 час из ответа `account/me`.

## Письма

- Локально — Mailpit (`http://127.0.0.1:54324`), e2e читает код через его API.
- Шаблоны подтверждения и восстановления в `supabase/templates/` на русском, с кодом крупно и без ссылок.
- SMTP Resend настраивается в `supabase/config.toml` через `env(...)`, локально выключен; переменные описаны в `.env.example`. Подключение домена и проверка доставляемости — этап 12.

## Первый администратор (Q-32)

1. Владелец регистрируется на сайте до подтверждения кода и закрывает страницу «Завершите регистрацию» (профиль не создаётся).
2. Запускает `npm run admin:bootstrap -- --email … --nickname … --name … --class …` с переменной `ADMIN_DATABASE_URL` (строка подключения к БД — секрет, только в локальном `.env`). Команда использует тот же сервис аккаунтов.
3. Сервис в одной транзакции проверяет, что администратора ещё нет и email подтверждён, создаёт профиль `admin` с `is_primary_admin = true` и датой вступления, без заявки, и пишет аудит. Повторный запуск отклоняется.

## Безопасность

- Роль не берётся из JWT и Auth metadata; при каждом запросе сервис читает профиль из БД.
- В `details` аудита только идентификаторы и названия полей; без паролей, кодов, токенов и текста анкеты.
- Пароль никогда не записывается в `sessionStorage`; черновик анкеты удаляется после успеха и при выходе.
- Анонимны только `catalog/classes` и `account/check-nickname`; остальные операции требуют подтверждённой сессии.
- Прямые вызовы каждой операции за каждую роль покрываются тестами (см. план).
