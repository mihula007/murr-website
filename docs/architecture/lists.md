# Списки: размер, постраничная загрузка и виртуализация

Правило введено решением владельца 11.11.2026. Краткая версия — раздел
«Списки» в [AGENTS.md](../../AGENTS.md); здесь подробности и реестр всех
списков приложения.

## Обязательный вопрос владельцу

Перед добавлением или изменением любого списка (операция API, возвращающая
массив, и экран, который его показывает) агент спрашивает владельца:
**может ли этот список содержать больше 50 элементов?** Вопрос описывает
экран (страница, маршрут, где на странице), кто его видит, что в строке и
как элементы появляются и исчезают со временем. Без такого описания владелец
не может ответить. Ответ записывается в реестр ниже до начала реализации.

Агент не отвечает за владельца и не выводит ответ из прототипа или
тестовых данных. Если владелец не ответил, список считается большим.

## Малый список (≤ 50, ответ «нет»)

- Операция возвращает все элементы одним ответом.
- Сервер всё равно ограничивает выборку порогом `SMALL_LIST_LIMIT`
  (`_shared/contracts/paging.ts`), выбирая на одну строку больше. Молча
  обрезать список нельзя: при превышении ответ несёт признак (например,
  `truncated`), а интерфейс сообщает, что показана только часть.
- Фильтр, поиск и сортировка на клиенте допустимы.
- Виртуализация не нужна.

## Большой список (> 50, ответ «да»)

### API

- Курсорная (keyset) пагинация. Запрос: `{ cursor?: string, limit?: number, …фильтры, search? }`
  (поля страницы — `pageRequestShape`), ответ — `Page<T>`:
  `{ items, nextCursor: string | null }` (`_shared/contracts/paging.ts`). Offset/номер страницы не используется:
  при вставке и удалении строк он пропускает и дублирует элементы и замедляется на глубоких страницах.
- Курсор непрозрачный (base64url JSON с ключом сортировки и `id`):
  `encodeCursor`/`decodeCursor`/`splitPage` из `_shared/http/cursor.ts`,
  ключ проверяется zod-схемой списка; испорченный курсор —
  `validation_failed` с полем `cursor`. Репозиторий выбирает `limit + 1`
  строк: лишняя означает, что есть следующая страница.
- Порядок однозначный: ключ сортировки + `id` как последний ключ, под него —
  индекс в миграции. Условие страницы — сравнение кортежа
  `(sort_key, id) > (cursor.sort_key, cursor.id)` в репозитории.
- `limit` по умолчанию `PAGE_SIZE` (50), максимум `MAX_PAGE_SIZE` (100).
- Фильтры, поиск и сортировка выполняются на сервере, потому что у клиента
  нет всех элементов. Смена фильтра начинает список с первой страницы.
  Для поиска подстроки по тексту — индекс (`pg_trgm` доступен на Free),
  проверить план запроса.
- Итоги и счётчики (общее число, распределение по классам) — отдельные
  поля или операции, считаются на сервере, а не по загруженным строкам.
- Права, проверка ввода и закрытые поля — как в любой операции `api`.

### UI

- Загрузка — `useInfiniteQuery` (TanStack Query) с `getNextPageParam: (last) => last.nextCursor`;
  ключ кеша включает фильтры и поиск.
- Отрисовка — TanStack Virtual (`@tanstack/react-virtual`) только через
  `src/components/virtual-list.tsx`: `VirtualList` для списков и сеток
  карточек (`ul`/`li`, колонки — `useGridColumns`), `useWindowList` +
  `VirtualSpacerRow` для таблиц, `pagingOf(query)` связывает их с
  `useInfiniteQuery`. Страница прокручивается окном (`useWindowVirtualizer`),
  высота строк измеряется. Это единственный файл, где разрешён `style` —
  только CSS-переменные `--virtual-*` (см. дизайн-систему).
- Следующая страница подгружается, когда виртуализатор доходит до конца
  загруженных строк; кнопка «Показать ещё» — запасной путь без прокрутки.
  Состояния: первая загрузка, догрузка, ошибка догрузки с повтором, пустой
  результат с учётом фильтра.
- Если под большим списком нужен другой блок, его выносят на вкладку или
  отдельную страницу: бесконечный список делает блок под ним недостижимым.
- Поле поиска — с задержкой (debounce) перед запросом, фильтры и поиск —
  в search-параметрах маршрута, чтобы ссылка открывала тот же список.
- Таблицы (TanStack Table) виртуализируются по строкам; правило «на узком
  экране строка — карточка» сохраняется.
- Доступность: у списка `aria-label`.
- Проверка на 375 и 1240 px и Playwright-сценарий с числом элементов больше
  одной страницы (пример — `e2e/lists.spec.ts`, фикстура `seedMembers`;
  найти элемент в списке — `scrollUntilVisible`).

## Списки текущих участников клана (Q-48)

Решение владельца 12.11.2026 — исключение из правила «> 50». Текущих
участников (член, офицер, администратор) может быть до 200, но их списки
всегда загружаются целиком одним ответом: без курсора, без серверных
фильтров и поиска. Фильтр, поиск и сортировка — на клиенте (`useQuery`).
Сервер ограничивает выборку порогом `MEMBER_LIST_LIMIT` (250), выбирая на
одну строку больше, и при превышении возвращает `truncated`; интерфейс
сообщает, что показана часть. Чтецы, аккаунты и прочие списки под это
исключение не попадают.

## Нумерованные страницы: публикации и рынок (Q-55)

Решение владельца 12.11.2026 — исключение из правила курсорной пагинации.
Ленты публикаций и торговых объявлений большие (> 50), но показываются
привычными нумерованными страницами по 50 записей с навигацией по номерам.

- API: `{ page, …фильтры, search? } → { items, page, pageCount, total }`;
  сортировка стабильная (время обновления ↓, `id`), чтобы страницы не
  перемешивались при равных значениях.
- Поиск, фильтр категории и подсчёт `total` — на сервере, клиент получает
  только одну страницу (`useQuery` с номером страницы в ключе, без
  `useInfiniteQuery` и без виртуализации — 50 строк).
- Номер страницы — в параметре маршрута, чтобы ссылка и «назад» работали.
- Известное следствие offset: если между переходами по страницам материал
  добавлен или удалён, запись может сдвинуться на соседнюю страницу. Владелец
  принял это ради привычной навигации.
- Исключение касается только этих двух лент. Другие большие списки остаются
  на курсорной пагинации.
