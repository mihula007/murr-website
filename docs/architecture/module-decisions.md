# Решения по модулям

Справочник принятых решений и инвариантов по этапам реализации. Читать раздел
модуля перед его изменением. Общие правила — `AGENTS.md`; требования —
[docs/requirements](../requirements/README.md).

## Клиент: оболочка, роль, сессия

- Оболочка (этап 2): меню и доступ к маршрутам описаны одной таблицей `src/app/navigation.ts`; `RouteGate` показывает «Нет доступа», если роли нет в таблице. Это клиентская проверка, не защита данных.
- Роль (этап 3): `AccessProvider` берёт её только из ответа `account/me` (профиль в БД), не из JWT и Auth metadata; `status` — `loading`, `guest`, `incomplete` (вошёл, регистрация не завершена — права гостя), `ready`, `error`. Dev-переключатель ролей удалён; для тестов у провайдера есть проп `role`. Демо `/#/dev/unsaved-demo` остаётся только в dev, `e2e/shell.spec.ts` проверяет его отсутствие в `dist/`. Кеш TanStack Query очищается при выходе и смене пользователя (`SessionProvider`).
- Смена роли во время сессии (этап 4): клиент кеша создаёт `createQueryClient` (`src/app/query-client.ts`); любой ответ `forbidden` от `api` перечитывает `me`, поэтому меню и доступ обновляются без выхода. Иначе `me` перечитывается при возврате на вкладку (после 60 с) и перезагрузке; данные всё равно защищены сервером при каждом вызове.
- Сессия в браузере бессрочная до явного выхода или очистки данных сайта (Q-35): `persistSession` + `autoRefreshToken`, ограничения сессий Supabase не включаются. Регистрация, вход, код, сброс пароля — [проект регистрации](registration-flow.md).
- Заставка показывается при первом открытии и если последняя активность старше 10 минут; метка — `murr-last-activity` в `localStorage` (запасной `sessionStorage`). Playwright-сценарии ставят метку через `skipSplash` из `e2e/helpers.ts`.
- `useUnsavedChangesGuard(isDirty)` подключать во всех формах, меняющих данные.
- Вход по email и паролю; email и сброс пароля подтверждаются шестизначным кодом из письма (`verifyOtp`), без redirect-ссылок, поэтому автоматическая обработка Auth redirect остаётся выключенной.

## Аккаунт и каталог (этап 3)

Схема `app` (классы, профили, заявки, ссылки, аудит) и одна функция `api` с операциями каталога и аккаунта.

## Заявки, состав, аккаунты, уведомления (этап 4)

- Мастер имеет те же права на разделы и операции, что офицер, кроме административного управления аккаунтами и журнала действий. В `roster` мастер может менять роли обычным членам и чтецам, а офицеров — понижать до члена, чтеца или кандидата; роль мастера назначает только администратор. В меню не показывается текущая роль пользователя. Офицер по-прежнему может переводить только обычного члена в чтецы; остальные переходы остаются полномочием администратора (ACL-14, ROS-07, ROS-12).

Таблица `user_notifications` и модули `applications` (очередь, карточка, прямое решение, новая заявка), `roster` (численность, состав, чтецы и смена ролей мастером), `accounts` (таблица аккаунтов, смена роли и блокировка, восстановление чтеца, правка ника и класса администратором), `notifications` (`notify(tx, …)` в транзакции действия). Изменение ника и класса — `accounts/set-profile`, только администратор, включая изменение собственного профиля и других администраторов; транзакция блокирует профиль цели, проверяет уникальность ника и активное удаление, меняет только отличающиеся значения и пишет одну запись аудита категории `profiles` с `changed_fields`, без значений и уведомления. Исторические снимки не меняются. Правило даты вступления — только `joinedOnAfterRoleChange` в `_shared/membership.ts`: переход кандидата или чтеца во внутреннюю роль ставит сегодняшнюю дату по Москве, переходы между внутренними ролями и блокировка её не меняют. Смена роли блокирует строки всех администраторов, затем цель (`FOR UPDATE`, один порядок) — защита основного и последнего администратора от гонок.

- В карточках состава фон выделяет только участника с ID текущей сессии; поиск и фильтр не меняют это сравнение.

## Голосования (этап 5)

Таблицы `votes`, `vote_options`, `vote_ballots` и модуль `votes` (список, карточка, создание, правка, голос, завершение, удаление). Итоги считаются запросом по голосам, отдельных счётчиков нет. Голос блокирует строку голосования `FOR SHARE`, завершение и удаление — `FOR UPDATE`: голос не проходит после завершения. Голосование по заявке создаётся только `applications/submit-to-vote`; завершение и удаление меняют статус заявки в той же транзакции, окончательное решение — `applications/final-decide` (только администратор). Ключи кеша клиента — `query-keys.ts` модулей `votes` и `applications`, чтобы модули сбрасывали кеш друг друга без цикла.

## События (этап 6)

Таблицы `events`, `event_attendance`, `event_templates` и модуль `events`. Всё время событий — московское (UTC+3 без перехода, Q-08, Q-44): перевод только `@contracts/moscow-time`, показ — `formatDateTimeMsk`; «ближайший выпуск» и «событие началось» считает сервер по `deps.now()`. Ответ — одна строка `(event_id, user_id)`, только до начала (Q-43), под блокировкой события `FOR SHARE`, в аудит не пишется (Q-45). Правка и удаление: автор-офицер, любой офицер для постоянных выпусков без автора (Q-47), администратор. Постоянные события создаёт задание Supabase Cron `events-ensure-weekly` (понедельник 00:00 МСК) вызовом `api` с заголовком `x-cron-secret` (`EVENTS_CRON_SECRET`, адрес и секрет — в Supabase Vault) или запасная кнопка офицера; дубликат исключён `UNIQUE (recurring_preset, starts_at)`.

- Вкладка актуальных событий использует `sections.events` из общего `notifications/summary` для красного счётчика новых событий; `activeCount` показывается отдельно обычным текстом. Отметка просмотра снимает только счётчик новизны. Строки текущего пользователя на странице события используют ID сессии.

## Группы и активность (этап 7)

- `events/get` выдаёт члену только участников его назначенной группы и эту группу; без назначения оба списка пустые. Собственный ответ и общие числа остаются в сводке. Офицер и администратор получают полный состав, включая архив (GRP-19).

Таблицы `event_groups`, `event_group_members`, `group_templates` (+ группы и участники шаблона), `event_activity_records`; модули `groups` и `activity`. Участник — в одной группе события (PK `(event_id, user_id)`), лидер — признак строки участника (частичный `UNIQUE`), поэтому перенос или удаление не оставляет лидера вне группы. Операции групп блокируют событие `FOR UPDATE` и отклоняют закрытое (`state_conflict`), в аудит не пишутся (Q-54). Страница события занимает доступную ширину; в шапке — свой ответ и кнопка «Обсуждение ивента» (Q-108), отдельной сводки ответов нет. Кнопки создания и шаблонов стоят в заголовке блока групп; карточки автоматически переходят на следующую строку, если не помещаются. Управление лидером, копирование ников, рассылка и удаление компактно размещены в одной строке карточки; лидер показывается как «ПЛ». Перетаскиваемая строка отображается целиком. В свободном списке заголовки ПА/ПЗ/БУ/ХП/БД сортируют людей, пустые значения остаются в конце; строка и участники групп показывают ник и иконку класса без подписи названия или ответа. На широком экране колонки участников и групп остаются рядом и прокручиваются независимо. Актуальные поля характеристик профиля перед показом приводятся к числам, исторический снимок не дополняется — у закрытого события столбцов характеристик нет. Тестовые числа задаются только локальной фикстурой `scripts/seed-dev.ts`. `events/close` в одной транзакции пишет итог посещения (текущий состав и все, кто в группах: в группе — «Посетил», вне группы с ответом — «Не посетил», без ответа — «Не отметился»; ник и класс копируются), отметку закрытия и аудит; повторное закрытие — `state_conflict`. Закрытое событие и его группы неизменяемы и не удаляются (FK `RESTRICT`). Аналитика считается запросами по итогу: процент — посещения / записи участника (Q-49), период — по дате начала МСК (Q-50); чтецы остаются в истории и сводке, но не в рейтинге (Q-53). Шаблоны групп — общая библиотека офицеров и администраторов, не больше 20 (GRP-12).

- В строках свободного списка и групп фон выделяет участника, чей ID совпадает с ID текущей сессии; прочие состояния строки (перетаскивание, лидерство, наведение) сохраняются.
- В рейтинге посещения `DataTable` принимает необязательный ID строки для подсветки; фильтрация и сортировка сохраняют выделение по ID.

## Публикации и рынок (этап 8)

Таблицы `publications`, `publication_attachments`, `market_listings` и модули `publications`, `market` (права раздельные: публикации — офицер свои, администратор любые; рынок — член и офицер свои, администратор любые). Содержимое — JSON Tiptap, проверяемый только `@contracts/rich-text` (Q-57); `search_text`, `excerpt`, `cover_url` вычисляет сервис при сохранении. Снятие с публикации возвращает в черновики; правка с `expectedUpdatedAt`, другая версия — `state_conflict`. Вложения — приватный bucket `publication-images`, загрузка в `uploads/<userId>/`, проверка сигнатуры при привязке, удаление файлов после коммита. Чужой черновик — `not_found`. Аудит: создание, изменение, публикация, снятие и удаление (категории `publications`, `market`; в `details` — id, заголовок, категория, статус).

- Категории рынка берутся из общего `MARKET_CATEGORIES` и `MARKET_CATEGORY_LABELS`; ограничение `market_listings_category_check` должно содержать те же значения. Добавление «Арены» меняет ограничение вперёд, но не требует преобразования существующих объявлений.

## Обсуждения (этап 9)

Таблицы `discussion_threads` (одна строка на родителя: событие, голосование, публикация или объявление; `CHECK` одного родителя, каскад от родителя), `discussion_messages`, `discussion_reactions`, `discussion_reads` и модуль `discussions`. Доступ к ветке следует родителю (`discussions/parents.ts`): писать можно в незавершённые событие и голосование, в опубликованный материал с включённым обсуждением; запись блокирует родителя `FOR SHARE`. Чат события и остальные обсуждения открываются отдельными окнами; кнопка события — на странице события (туда ведут уведомления) и на карточке события в расписании или на главной. Прочтение — одна отметка «прочитано до» на пользователя и ветку. Упоминания `@ник` и ответы — уведомления `discussion_mention`/`discussion_reply` через `notify`. Открытая ветка опрашивает `discussions/changes` раз в 30 с только при видимой вкладке (Q-58), Realtime не используется; аудита нет (Q-63). Ветка грузится страницами вверх (`ReverseVirtualList` в `virtual-list.tsx`).

## Уведомления и главная (этап 10)

Таблица `section_views` (отметка просмотра раздела на пользователя) и операции `notifications/*` в модуле `notifications`. Колокольчик — кандидат и внутренние роли; панель — последние 50 (Q-64), прочтение — по одному или «прочитать все». Шапка опрашивает одну операцию `notifications/summary` (непрочитанные + счётчики разделов) раз в 60 с при видимой вкладке (Q-66). Новизна раздела — объекты чужих авторов после отметки; первая отметка ставится при первом доступе (Q-67). Новые источники `notify`: группа и пати-лидер (источник — событие, одно на участника), смена роли; ответы на событие автору не приходят (Q-65). Главная внутренних ролей берёт события из `events/list` (тот же кеш, что расписание), топ — `activity/month-top`, состав — `roster/list`; отдельной операции нет. Прочтения и отметки просмотра в аудит не пишутся.

- На вкладке актуальных событий красное число — только непросмотренные новые события из того же сводного ответа; после открытия событий оно исчезает, а число актуальных остаётся обычным текстом.

## Рассылки, администрирование, удаление (этап 11)

Журнал действий в администрировании использует `ScrollableVirtualList` с внутренней областью примерно на 15 записей; при прокрутке сохраняется курсорная подгрузка.

Таблицы `broadcast_drafts`, `broadcast_templates`, `user_deletions` и модули `broadcasts`, `deletion`. Рассылки — только подготовка (Q-22): текст из события, голосования или группы составляет `broadcasts/prefill`, черновики и шаблоны общие для офицеров и администраторов (не больше 50 и 20, Q-69, Q-70), файлы — только метаданные. Вкладка «Подписки» вызывает `broadcasts/subscriptions`: только офицер и администратор получают курсорные страницы ников, ролей внутреннего состава и флагов наличия/блокировки трёх мессенджеров; поиск по нику выполняется сервером и использует trigram-индекс (Q-112). Клиент использует `ScrollableVirtualList` с внутренней областью примерно на 15 строк; заголовки трёх каналов разнесены по колонкам и выравнены со значками. Для отправки офицер/администратор может временно исключить получателя BRC-16: список уникальных подходящих профилей объединяет выбранные каналы, ищется по нику на сервере и загружается курсором `(ник, id)`; снятая отметка исключает профиль из всех выбранных каналов текущего объявления. Исключения не хранятся в черновиках/шаблонах. При отправке все каналы применяют один набор исключённых ID; числа считаются по каналам после исключений, а одна запись `broadcast_sent` добавляет общее число исключённых без ников. Закрытые поля аккаунта в ответы не входят. Администрирование: поиск и сортировка аккаунтов на сервере, карточка, смена пароля другого аккаунта через Auth Admin API (Auth сам завершает сеансы цели, Q-72), журнал (`audit/list`, курсор). Безвозвратное удаление (Q-73–Q-75) — только не-администратора: служебная запись без FK на профиль → файлы Storage → одна транзакция (черновики, профиль с каскадами и `SET NULL`, аудит с ником и email) → Auth; каждый этап отмечается, повтор кнопкой продолжает с места сбоя. Пока запись есть, `loadActor` возвращает `deleted`, любой вызов — `account_deleted`, клиент выходит локально. Новая ссылка на `profiles` в миграции обязана получить правило `ON DELETE` по таблице данных плана этапа 11 и проверку в `tests/server/user-deletion.test.ts`.

## Telegram (этап 13)

Q-76–Q-96, [проект](telegram-integration.md). Таблицы `telegram_links`, `telegram_link_codes`, `telegram_announcements`, `telegram_event_messages`; модуль `telegram` и отправка в `broadcasts`. Вебхук бота — маршрут `telegram/webhook` той же функции `api`, проверка — заголовок `X-Telegram-Bot-Api-Secret-Token`; Bot API — через `fetch` (`_shared/telegram/gateway.ts`), токен не логируется. Без `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` и `TELEGRAM_WEBHOOK_SECRET` интеграция выключена (`telegram_unavailable`). Привязка — одноразовый код `t.me/<бот>?start=` (хеш, 15 минут), один Telegram на аккаунт. Анонс события — с кнопками ответа, уже ответившим на событие не отправляется во всех мессенджерах (Q-109); ответ кнопкой и с сайта — одна функция `saveAnswer` (`events/service.ts`); у участника активно одно сообщение на событие (прежнее теряет кнопки); ответ на сайте перерисовывает его фоново (`_shared/background.ts`, `EdgeRuntime.waitUntil`; локально нужен `[edge_runtime] policy = "per_worker"`). Одна запись аудита на отправку; привязка, отвязка и ответы в аудит не пишутся. Вложения рассылок отменены (Q-82), текст — до 3800 символов (Q-91). ВКонтакте и MAX не подключены.

## Характеристики персонажей и рейтинг силы (этап 14)

Пять необязательных числовых показателей и текстовый источник относятся к текущему персонажу в `profiles`; отдельная история не создаётся. Читать и менять карточку характеристики может только `admin`; блок сохраняется одной операцией `accounts/set-character-stats` (меняются только переданные поля с новым значением) и одной записью аудита `character_stat_changed` с `changed_fields` и `stat_changes` («ПА: 100 → 125500»), Q-106. Прежняя `accounts/set-character-stat` (одно поле) оставлена для уже выложенного клиента и идёт через тот же код. `roster/list` и `events/get` (свободный список группы) отдают только пять показателей внутренним ролям; источник остаётся только в ответе `accounts/get`. Главная переиспользует кеш `roster/list`, не добавляя вызов функции; рейтинг строится по полному составу Q-48, сортировка — на клиенте; на узком экране без внутренней прокрутки — 15 карточек и «Показать всех» (Q-107). Кандидаты, чтецы и гости не получают рейтинг или показатели. Изменение состава списка и защита от удаления следуют правилам этапов 4 и 11.

- В рейтинге силы на главной фоновая подсветка использует ID текущей сессии, а не текущую позицию; сортировка и фильтр класса не сдвигают её на другого участника.

## MAX (этап 15)

Q-99–Q-101, [проект](max-integration.md). Модуль `max` — копия устройства `telegram` с таблицами `max_links`, `max_link_codes`, `max_announcements`, `max_event_messages` (`message_id` — строка `mid`). Общее для мессенджеров — `_shared/messenger/` (код привязки, секрет, данные кнопок, HTML анонса, `syncEventMessages`). Вебхук — `max/webhook`, секрет — `X-Max-Bot-Api-Secret`; Bot API через `fetch`, токен в заголовке `Authorization`. Без `MAX_BOT_TOKEN`, `MAX_BOT_USERNAME`, `MAX_WEBHOOK_SECRET` — `max_unavailable`. `broadcasts/send` принимает `channels` (по умолчанию Telegram) и пишет одну запись аудита с разбивкой по каналам (`telegram_sent`, `max_sent`, `*_failed`). Ответ на событие (сайт или кнопка) фоново обновляет активные сообщения во всех мессенджерах.

## ВКонтакте (этап 16)

Q-102, [проект](vk-integration.md). Модуль `vk` по устройству `max`, таблицы `vk_links`, `vk_link_codes`, `vk_announcements`, `vk_event_messages` (`message_id` — `conversation_message_id`). Вебхук — Callback API сообщества, маршрут `vk/webhook`: проверка `group_id` и поля `secret`, ответ — текст `ok` (маршрут возвращает `Response`), на `confirmation` — код из `groups.getCallbackConfirmationCode`. API — `POST` формы с `access_token` в теле. Привязка — `ref` первого сообщения по ссылке `vk.me`. Сообщения — простой текст. Без `VK_BOT_TOKEN`, `VK_GROUP_ID`, `VK_CALLBACK_SECRET` — `vk_unavailable`.
