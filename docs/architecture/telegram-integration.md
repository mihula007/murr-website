# Интеграция Telegram: технический проект

Статус: **проект для согласования** (14.11.2026). Требования — [19-telegram.md](../requirements/19-telegram.md), решения владельца — Q-22, Q-76–Q-96. Документ не разрешает реализацию; после согласования по нему составляется план этапа.

## Ограничения, из которых исходит проект

- Одна Edge Function `api` (AGENTS.md): бот не получает своей функции. Вебхук Telegram — ещё один маршрут `api`.
- `verify_jwt = false` у `api` уже стоит (`supabase/config.toml`): Telegram не присылает JWT. При выкладке в облако функция публикуется так же (`--no-verify-jwt`), проверка вебхука — секретным заголовком.
- В функции не импортируется `@supabase/supabase-js`, внешние API вызываются через `fetch` (холодный старт). Bot API — тоже через `fetch`, без библиотеки бота: нужны пять методов.
- Слои: обработчик → сервис → репозиторий; SQL только в репозиториях; правила — в TypeScript.
- Supabase Free: нажатие кнопки — один вызов функции. При 200 участниках и нескольких анонсах в неделю это тысячи вызовов в месяц при квоте в сотни тысяч. Перед реализацией перепроверить актуальные лимиты функции Free (время выполнения запроса и CPU).
- Секреты только в `.env` и Supabase Secrets; ни одной переменной `VITE_*` для Telegram.

## Схема

```
Личный кабинет ──telegram/link-start──▶ api ──▶ код привязки (хеш) в БД
      │                                   ▲
      └─ ссылка t.me/<бот>?start=<код>     │ POST /api/telegram/webhook
                         Telegram ─────────┘  (заголовок секрета)
«Рассылка» ──broadcasts/send──▶ api ──sendMessage / editMessage*──▶ Telegram
Карточка события ──events/respond──▶ api ──editMessageText (фон)──▶ Telegram
```

## Конфигурация

| Переменная                | Где                                     | Назначение                                                                                       |
| ------------------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `TELEGRAM_BOT_TOKEN`      | `.env`, Supabase Secrets                | Секрет. Токен бота от BotFather. Уже есть в `.env.example`.                                      |
| `TELEGRAM_WEBHOOK_SECRET` | `.env`, Supabase Secrets                | Секрет. Значение `secret_token` вебхука, сверяется с `X-Telegram-Bot-Api-Secret-Token`.          |
| `TELEGRAM_BOT_USERNAME`   | `.env`, Supabase Secrets                | Не секрет, но только серверная: сервер сам собирает ссылку `t.me/...`, клиенту `VITE_` не нужна. |
| `SITE_URL`                | `.env`, Supabase Secrets                | Адрес сайта для ответов бота (TGM-09).                                                           |
| `TELEGRAM_API_BASE`       | только локально и в e2e (необязательна) | Подмена `https://api.telegram.org` на фальшивый Bot API в тестах.                                |

Без токена интеграция выключена: `deps.telegram = null`, операции привязки и отправки отвечают новым кодом ошибки `telegram_unavailable` (503), кабинет и «Рассылка» показывают «Telegram не подключён». Каркас по-прежнему работает без `.env`.

## Данные (одна миграция)

```sql
-- Связь аккаунта с Telegram (TGM-04, TGM-05). Удаление пользователя — каскад.
create table app.telegram_links (
  user_id uuid primary key references app.profiles (id) on delete cascade,
  telegram_user_id bigint not null unique,
  chat_id bigint not null,
  username text,            -- только для показа
  display_name text not null,
  linked_at timestamptz not null default now(),
  blocked_at timestamptz    -- бот заблокирован (TGM-08)
);

-- Одноразовый код привязки: хранится только SHA-256, один на пользователя.
create table app.telegram_link_codes (
  user_id uuid primary key references app.profiles (id) on delete cascade,
  code_hash text not null unique,
  expires_at timestamptz not null
);

-- Тема и текст анонса события: нужны, чтобы перерисовать сообщение со строкой
-- ответа. HTML строится при отправке. Отдельные анонсы не хранятся (Q-80).
create table app.telegram_announcements (
  id uuid primary key default gen_random_uuid(),
  event_id uuid not null references app.events (id) on delete cascade,
  subject text,
  body text not null,
  created_at timestamptz not null default now()
);

-- Активное сообщение участника по событию (TGM-22): ровно одно.
create table app.telegram_event_messages (
  event_id uuid not null references app.events (id) on delete cascade,
  user_id uuid not null references app.profiles (id) on delete cascade,
  announcement_id uuid not null references app.telegram_announcements (id) on delete cascade,
  chat_id bigint not null,
  message_id bigint not null,
  sent_at timestamptz not null default now(),
  primary key (event_id, user_id)
);
```

- RLS включён без политик, GRANT для `anon`/`authenticated` не выдаются (pgTAP).
- Новые ссылки на `profiles` — `ON DELETE CASCADE`; проверки добавляются в `tests/server/user-deletion.test.ts` (правило этапа 11).
- Анонсы, на которые больше не ссылается ни одно сообщение, удаляются в той же транзакции, что и замена сообщения, — таблица не растёт.
- `broadcast_drafts`: удалить столбец `attachments` (Q-82). Лимит текста черновиков и шаблонов — 3800 (TGM-17), `CHECK` меняется той же миграцией.

## Серверные модули

`supabase/functions/_shared/telegram/`:

| Файл               | Содержание                                                                                                                                                                                                                                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `gateway.ts`       | `TelegramGateway` через `fetch`: `sendMessage`, `editMessageText`, `editMessageReplyMarkup`, `answerCallbackQuery`, `setWebhook`. Результат — `ok` / `blocked` (403) / `not_modified` / `failed`; 429 — пауза `retry_after` и один повтор. Токен никогда не попадает в логи (URL с токеном не печатается). |
| `render.ts`        | HTML-текст сообщения (экранирование `< > &`, тема в `<b>`), строка «Ваш ответ: …», клавиатуры: три ответа / «Изменить решение».                                                                                                                                                                            |
| `callback-data.ts` | `callback_data` ≤ 64 байт: `a:<eventId>:<y\|m\|n>` — ответ, `c:<eventId>` — «Изменить решение». Разбор zod; данные кнопки не доверенные, права проверяются заново.                                                                                                                                         |
| `repository.ts`    | SQL всех четырёх таблиц и выборка получателей с текущими ответами на событие.                                                                                                                                                                                                                              |
| `service.ts`       | Привязка, отвязка, состояние, разбор вебхука, отправка анонса, обновление сообщения после ответа на сайте.                                                                                                                                                                                                 |

`AppDeps` получает `telegram: TelegramGateway | null` и `background(task)` — фоновую задачу после ответа: в функции через `EdgeRuntime.waitUntil` (только в `api/index.ts`, общий код без глобалов Deno), в тестах Node — дожидается выполнения.

`events/service.ts`: ядро `respondToEvent` выносится в `saveAnswer(deps, viewer, eventId, answer)`; его вызывают и сайт, и кнопка Telegram — правила Q-43 и роли общие (TGM-18).

### Операции `api`

| Маршрут                 | Кто                 | Что делает                                                                                 |
| ----------------------- | ------------------- | ------------------------------------------------------------------------------------------ |
| `telegram/status`       | член, офицер, админ | `{ configured, linked, username, displayName, blocked }`                                   |
| `telegram/link-start`   | член, офицер, админ | Новый код (32 случайных байта, base64url — 43 символа), заменяет прежний; ответ `{ url }`. |
| `telegram/unlink`       | член, офицер, админ | Удаляет связь и код.                                                                       |
| `telegram/webhook`      | Telegram (секрет)   | Обрабатывает `message` (`/start`) и `callback_query`.                                      |
| `broadcasts/recipients` | офицер, админ       | `{ count }` для окна подтверждения (не список, реестр списков не затрагивает).             |
| `broadcasts/send`       | офицер, админ       | `{ subject, body, eventId? }` → `{ sent, failed }`.                                        |

## Сценарии

### Привязка (TGM-02–TGM-04)

1. Кабинет: «Привязать Telegram» → `telegram/link-start` → на месте кнопки появляется ссылка «Открыть бота» (обычный `<a target="_blank">`, а не `window.open` после запроса — иначе мобильный браузер блокирует окно).
2. Пользователь жмёт «Запустить» в Telegram → апдейт `/start <код>` → вебхук: хеш кода, проверка срока, в одной транзакции удаляется код и записывается связь (`UNIQUE telegram_user_id` защищает от гонки двух аккаунтов). Бот отвечает подтверждением.
3. Кабинет перечитывает `telegram/status` при возврате на вкладку (`refetchOnWindowFocus` этого запроса).

### Отправка анонса (TGM-11–TGM-17, TGM-20, TGM-22)

1. Проверки: роль, длина, для анонса события — событие существует, не закрыто, не началось (по `deps.now()`).
2. Получатели: внутренние роли с `blocked_at is null`, для события — с текущим ответом.
3. Для анонса события — строка `telegram_announcements`.
4. Отправка пулом до 20 одновременных запросов с темпом ≤ 25 сообщений в секунду (лимит Telegram — около 30 в секунду на бота, 1 в секунду на чат). 200 получателей — около 10 с, внутри лимита времени запроса функции.
5. На каждого успешного получателя анонса события: в короткой транзакции заменяется строка `telegram_event_messages`, прежний `message_id` возвращается; затем прежнее сообщение перерисовывается только текстом своего анонса без кнопок (TGM-22). Сетевые вызовы — вне транзакций БД.
6. 403 → `blocked_at = now()`; прочие ошибки — счётчик `failed`.
7. Одна запись аудита (TGM-25), ответ `{ sent, failed }`, клиент показывает toast.

Двойная отправка: кнопка блокируется на время запроса; серверной защиты от повторной отправки того же текста нет (Q-96: достаточно подтверждения и блокировки кнопки).

### Нажатие кнопки (TGM-18–TGM-23)

1. Проверка секрета, разбор апдейта zod (неизвестные апдейты — 200 без действий).
2. Связь по `from.id`; нет связи → всплывающее «Аккаунт не привязан», кнопки сообщения снимаются.
3. Строка `telegram_event_messages` по `(eventId, userId)` должна совпадать с `chat_id` и `message_id` нажатого сообщения; иначе сообщение неактивно → «Анонс устарел», кнопки снимаются (TGM-22). Так кнопка всегда строго привязана к своему сообщению и событию.
4. `a:` → `loadActor` пользователя → `saveAnswer`; ошибка `forbidden` / `state_conflict` / `not_found` → пояснение и снятие кнопок. Успех → сообщение перерисовывается со строкой ответа и кнопкой «Изменить решение».
5. `c:` → те же проверки, без записи в БД → три кнопки.
6. Всегда `answerCallbackQuery` (иначе в Telegram крутится индикатор).

Вебхук отвечает 200 и при внутренней ошибке (она пишется в лог): иначе Telegram повторяет апдейт. Повтор нажатия безопасен — ответ тот же; повтор `/start` с уже использованным кодом даёт сообщение «ссылка устарела» — допустимо.

### Ответ на сайте (TGM-21)

После коммита `events/respond` через `deps.background` перерисовывает активное сообщение участника, если оно есть. Сбой Telegram или «сообщение не изменено» только логируются; ответ сайта не ждёт Telegram.

## Локальная разработка

- **Отдельный бот для разработки** (Q-95): у бота один вебхук, поэтому локальный туннель переключил бы на себя рабочего бота. Локально в `.env` — токен тестового бота.
- Туннель (Q-87) — библиотека в devDependencies, новая зависимость требует решения владельца с записью причины в AGENTS.md. Варианты:

| Библиотека                   | Плюсы                                                        | Минусы                                                                        |
| ---------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| `cloudflared` (выбран, Q-95) | Быстрый туннель Cloudflare без аккаунта и ключа; стабильный. | npm-обёртка при установке скачивает официальный бинарник Cloudflare с GitHub. |
| `localtunnel`                | Чистый JS, без аккаунта.                                     | Публичные серверы часто недоступны.                                           |
| `@ngrok/ngrok`               | Официальный SDK, стабильный.                                 | Нужен аккаунт ngrok и ещё один секрет (`NGROK_AUTHTOKEN`).                    |

- `npm run telegram:dev` (`scripts/telegram-dev.ts`): поднимает туннель к `127.0.0.1:54321`, вызывает `setWebhook` (`/functions/v1/api/telegram/webhook`, `secret_token`, `allowed_updates: [message, callback_query]`, `drop_pending_updates`), при остановке — `deleteWebhook`. Функции работают через существующий `npm run supabase:functions` (`--env-file .env`).
- `npm run telegram:webhook` — однократная регистрация вебхука облачной функции владельцем (токен берётся из `.env`, не печатается).

## Тесты

- Vitest: `render.ts` (экранирование, длина), `callback-data.ts`.
- `npm run test:server`: фальшивый `TelegramGateway` записывает вызовы. Привязка (срок, повтор, чужой Telegram, гонка), отвязка, отправка за каждую роль, получатели (чтец, кандидат, заблокированный бот не получают), замена активного сообщения, нажатия (неверный секрет, непривязанный, неактивное сообщение, начавшееся событие, чтец), синхронизация ответа с сайта, аудит одной записью, удаление пользователя.
- pgTAP: новые таблицы закрыты для Data API, `UNIQUE` и FK.
- Playwright: E2E-08 с фальшивым Bot API (небольшой HTTP-сервер в e2e, `TELEGRAM_API_BASE`): тест сам шлёт апдейты в вебхук и проверяет кабинет, «Рассылку» и карточку события.

## Безопасность

- Токен и секрет вебхука — только на сервере; сравнение секрета — за постоянное время.
- Код привязки хранится хешем, одноразовый, 15 минут; в URL — только он, личных данных нет.
- `callback_data` не доверенные: каждое нажатие проходит проверку связи, активного сообщения, роли и состояния события.
- ID Telegram и username — личные данные: удаляются при удалении пользователя, в аудит не пишутся.
