# Функциональные требования по прототипу Murrclan

Дата исследования: 08.11.2026. Статус: **проект требований для согласования**.

Документы описывают функциональный контракт для последующей реализации, восстановленный по локальному прототипу и уточнённый ответами владельца. Это не утверждение, что новая React-основа уже реализует эти функции, и не разрешение начинать их перенос. Название Murrclan и игра Perfect World видны в прототипе; официальное название нового приложения отдельно не утверждено.

Общее требование: при уходе с любой страницы с несохранёнными изменениями пользователь получает предупреждение и может отменить переход. Для каждого нового действия, меняющего состояние системы, явно определить, требуется ли его запись в журнал аудита; обязательные события аудита перечислены в ADM-11.

## Как пользоваться

1. Согласовать [роли](01-roles.md), [границы блоков](02-page-map.md) и [открытые решения](17-open-questions.md).
2. Для реализуемого блока использовать его требования и сценарии приёмки. В задачах и проверках ссылаться на ID, например `EVT-04`.
3. Исполнение требования отмечать отдельно: не начато / реализовано / проверено / принято. Наличие пункта в этой документации не означает прохождение приёмки.
4. При изменении правила обновлять связанный документ и сквозные сценарии. Не переиспользовать ID удалённого требования для другого смысла.

## Достоверность

- **UI** — действие или состояние проверено во встроенном браузере. Конкретный объём проверки указан в [журнале исследования](18-research.md); просмотр формы не означает проверку всех её ограничений.
- **Код** — правило уточнено чтением `prototype/index.html`; оно не обязательно воспроизведено через интерфейс. В каждом блоке перечислены функции-источники.
- **Предложение** — ожидаемое поведение для исправления противоречия либо необходимое уточнение новой реализации. Требует решения владельца; не выдаётся за работающую функцию прототипа.
- **Вопрос Q-xx** — неоднозначность. До ответа соответствующая часть контракта остаётся предварительной.

Если у перечня требований указан общий источник, он распространяется на пункты перечня; исключения отмечены отдельно. Требования с источником «Код» остаются кандидатами на перенос, а не автоматически утверждёнными правилами продукта. Ошибки прототипа собраны отдельно и не должны становиться эталоном реализации.

## Общие ограничения контракта

- `GEN-01` Роль, состояние заявки и авторство объекта — разные признаки. Права проверяются по роли и объекту, а не по подписи кнопки или видимости меню.
- `GEN-02` Запрет действия должен распространяться на саму операцию. В будущей серверной версии изменение браузерного состояния не даёт дополнительных прав. Это требование переноса, а не свойство локальной защиты прототипа.
- `GEN-03` После успешного действия связанные экраны показывают согласованное состояние: список, карточка, счётчики, кабинет и аналитика не должны противоречить друг другу. Ошибка сохранения не должна выдаваться за успех. Это предложение к надёжности новой версии.
- `GEN-04` Персональные поля анкеты, email и ссылки заявки не становятся общедоступными вместе с исходным кодом. Секреты и тестовые пароли не включаются в требования и снимки экрана.
- `GEN-05` Данные прототипа локальны. Хранение в localStorage/IndexedDB и отсутствие межустройственной синхронизации — ограничения демонстрации, а не желаемые ограничения рабочего сайта.
- `GEN-06` Дизайн экранов, схема БД и серверные API остаются проектом. Вход по email и паролю с подтверждением кодом, бессрочное хранение личных данных до удаления аккаунта и Resend Free для Auth согласованы. Доставка ботами: Telegram — [19-telegram.md](19-telegram.md); ВКонтакте и MAX не подключаются.

## Сквозная приёмка

| Сценарий                         | Последовательность и ожидаемый результат                                                                                                                                                                                                                                                                               | Контракт                |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| E2E-01 Вступление с голосованием | Гость заполняет регистрацию и подтверждает email → система сохраняет профиль и автоматически создаёт заявку → офицер создаёт связанное голосование → участники голосуют → офицер или администратор видит итоги и завершает голосование с решением принять → кандидат получает внутренний доступ и появляется в составе | ACC, APP, VOT, ROS, NTF |
| E2E-02 Прямой приём              | Офицер принимает новую заявку без голосования → членство и дата вступления фиксируются → внутренние разделы открыты                                                                                                                                                                                                    | APP, ROS                |
| E2E-03 Архив ивента              | Создание → ответы → распределение по группам → лидер → закрытие → снимок посещений с удалением данных удалённого пользователя и сохранением истории чтецов → аналитика и экспорт                                                                                                                                       | EVT, GRP, ACT           |
| E2E-04 Жизненный цикл материала  | Редактор сохраняет черновик → участник его не видит → публикация → участник читает и обсуждает → снятие с публикации скрывает материал от читателей                                                                                                                                                                    | PUB, DSC                |
| E2E-05 Собственное объявление    | Член/офицер создаёт объявление → редактирует своё → другой участник не получает управление → администратор видит и редактирует любое, включая черновик                                                                                                                                                                 | MKT, ACL                |
| E2E-06 Ограничение доступа       | Выход из клана или блокировка администратором → чтец может войти, видеть и редактировать свой профиль, остальные права соответствуют гостю → офицер или администратор восстанавливает его как члена с новой датой вступления, действие попадает в аудит                                                                | ACL, ADM, HOM           |
| E2E-07 Подготовка рассылки       | Из ивента/голосования/группы открывается заполненная форма → выбор каналов → сохранён черновик → нет ложного сообщения об отправке                                                                                                                                                                                     | BRC                     |
| E2E-08 Анонс события в Telegram  | Член привязывает Telegram в кабинете → офицер отправляет анонс события → член отвечает кнопкой в Telegram → ответ виден на сайте → смена ответа на сайте обновляет сообщение                                                                                                                                           | TGM, EVT, ACC           |

Сценарии — список будущей приёмки. Какие из них фактически пройдены в прототипе полностью или частично, указано в журнале исследования.

Автоматизация в новом приложении (Playwright, desktop и mobile; приёмка владельцем не проводилась):

- E2E-02 — реализовано на этапе 4: `e2e/applications.spec.ts` (приём офицером, внутреннее меню, место в составе, дата вступления, рост численности, аудит и уведомление).
- E2E-07 — реализовано на этапе 11: `e2e/broadcast.spec.ts` (подготовка из события, голосования и группы, черновик без отправки). Администрирование и удаление пользователя — `e2e/admin.spec.ts`.
- E2E-06 — реализовано на этапе 4: `e2e/membership.spec.ts`. Самостоятельного выхода из клана нет, поэтому «выход» проверяется блокировкой администратором (Q-38); восстановление выполняет офицер, события проверяются в журнале аудита запросом к локальной БД (журнал в интерфейсе — этап 11).
