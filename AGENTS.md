# Проект: веб-сайт игровой гильдии

## Назначение и контекст

Веб-приложение для участников гильдии из видеоигры. Название игры и
официальное название проекта пока не уточнены.

Будущие функциональные направления, заявленные владельцем проекта:

- Авторизация и роли: обычный пользователь, офицер, администратор.
- Заявки на вступление, голосование по заявкам и комментарии.
- Личный кабинет с информацией о персонаже.
- Регулярные события и отметки пользователей о присутствии.
- Публикация торговых предложений.
- Сводные таблицы пользователей.
- Интеграции с ботами Telegram, MAX и VK: уведомления и ответы через кнопки.

Это контекст для будущей архитектуры, а не задание реализовать эти функции
на текущем этапе. Матрица разрешений и подробные правила ещё не определены.

## Критически важно: публичный репозиторий и секреты

Владелец разрешил публичное размещение исходного кода. Защита секретов —
обязательное условие любых изменений, коммитов, сборок и публикаций.

- Все реальные секреты для локальной разработки записывать в `.env`,
  исключённый из Git через `.gitignore`. Правило распространяется также
  на вложенные env-файлы, варианты окружений и их локальные копии.
- Никогда не записывать значения секретов в исходники, документацию,
  тесты, примеры, логи, сообщения коммитов или публикуемые артефакты.
- В корне обязательно поддерживать `.enc.example` — шаблон с названиями
  всех ожидаемых переменных, включая секреты, но без реальных значений.
  Имя `.enc.example` задано владельцем; это обычный текстовый шаблон,
  а не зашифрованное хранилище. При добавлении или переименовании
  переменной одновременно обновлять шаблон и пояснение её назначения.
- Пустые значения в шаблоне не означают, что все интеграции обязательны
  для запуска: отмечать переменные будущих или необязательных функций.
- Переменные `VITE_*` включаются в браузерную сборку и являются публичными.
  Допускать в них только публичную конфигурацию, например URL Supabase
  и publishable key. Серверные ключи Supabase, пароли и токены ботов
  никогда не должны иметь префикс `VITE_` или попадать в клиентский код.
- Для опубликованных Edge Functions передавать секреты в защищённое
  хранилище Supabase; локальный `.env` не публиковать вместе с функциями.
  Для CI/CD использовать GitHub Actions Secrets, когда они потребуются.
- Перед коммитом проверять подготовленные изменения и отсутствие
  отслеживаемых файлов с секретами. `.gitignore` не удаляет файлы,
  ранее добавленные в Git. При обнаружении утечки остановить публикацию,
  сообщить владельцу и организовать отзыв или замену скомпрометированного
  секрета; одного удаления значения из последнего коммита недостаточно.

Документация: [переменные Vite](https://vite.dev/guide/env-and-mode),
[секреты Supabase Edge Functions](https://supabase.com/docs/guides/functions/secrets).

## Подтверждённые ограничения и предпочтения

- Обязательное условие архитектуры: backend, включая серверные функции
  и базу данных, должен работать в рамках бесплатного тарифа Supabase.
  Не закладывать обязательные платные сервисы, платные возможности
  Supabase или дополнительный VPS.
- Клиентский хостинг: бесплатный GitHub Pages с подключённым собственным
  доменом. Конкретное доменное имя пока не указано.
- Не предполагать наличие отдельного Node.js-сервера приложения.
- Язык приложения: TypeScript.
- Менеджер пакетов: npm, обычные зависимости в `node_modules`.
- Предпочтительные UI-инструменты: shadcn/ui и Tailwind CSS 4.
- При выборе дополнительных библиотек отдавать предпочтение TanStack,
  если решение подходит задаче и не создаёт ненужной сложности.
- Использовать доступные навыки superpowers там, где они применимы.
- Основной язык обсуждения и проектной документации: русский.

## Согласованная основа стека

- React: клиентское веб-приложение.
- Vite: сборка приложения и сервер разработки.
- TanStack Router: маршрутизация клиентского приложения.
- Supabase: backend, серверные функции и база данных в рамках Free.
- GitHub Pages: размещение собранного клиента с собственным доменом.

Выбор React + Vite + TanStack Router принят вместо первоначально
обсуждавшегося Next.js. Причина: клиент размещается как статические
файлы, а backend сосредоточен в Supabase без отдельного сервера.
Next.js и TanStack Start в выбранную основу не входят.

## Инструменты и решения инициализации

- Node.js 24 LTS; версия npm зафиксирована в `packageManager`.
- Все версии прямых npm-зависимостей точные; `package-lock.json` хранится
  в Git. Для воспроизводимой установки использовать `npm ci`.
- TypeScript strict с отдельными конфигурациями клиента, инструментов
  Node.js и тестов. Типы Node не добавлять в клиентскую конфигурацию.
- Vitest и React Testing Library — тесты клиентской основы; Playwright
  — браузерные проверки собранного сайта на desktop и mobile.
- Oxlint — линтер (название «osxlint» интерпретировано как опечатка).
  Prettier — форматтер. ESLint не установлен.
- TanStack Query — клиентский кеш. TanStack Table и Form добавлять
  вместе с задачами, которые их требуют; пока они не установлены.
- shadcn/ui: `components.json`, базовый Button, Radix Slot и CSS-токены
  Tailwind 4. Новые компоненты добавлять по необходимости.
- Supabase JS SDK и CLI 3. Браузер использует publishable key; служебные
  серверные ключи в клиенте запрещены. Пакет SSR не нужен.

Сопутствующие инструменты и defaults выбраны исполнителем в рамках сетапа.
Точные версии смотреть в `package.json` и `package-lock.json`.

## Архитектура и решения

Принятые архитектурные решения:

- Клиент — React-приложение, собираемое Vite в статические файлы для
  GitHub Pages. Серверная логика не выполняется на клиентском хостинге.
- Маршруты объявлены кодом в `src/routes/`; TanStack Router использует
  hash history, например `/#/events`. Это выбранный исполнителем default
  для прямых ссылок на Pages без серверных rewrites. Vite `base: './'`
  позволяет использовать собственный домен и путь репозитория.
- Провайдеры и сборка приложения находятся в `src/app/`; доменные модули
  добавлять в `src/features/` по мере разработки без пустых абстракций.
- Браузерный клиент Supabase создаётся лениво. Без публичной конфигурации
  возвращается `null`; статический каркас работает без `.env` и сети.
  Сборка отклоняет неизвестные переменные `VITE_*` и серверные ключи.
- Способ входа пока не реализован. Автоматическая обработка Auth redirect
  отключена до согласования PKCE callback, совместимого с hash-router.
- Серверные обработчики, включая будущие интеграции с ботами,
  размещаются в Supabase Edge Functions; данные и необходимые операции
  БД — в Supabase Postgres. Сейчас есть только локальная конфигурация и
  каталоги для миграций и функций, без прикладной схемы и обработчиков.
- Новые таблицы локально не открываются через Data API автоматически;
  при их создании нужны явные GRANT и RLS-политики в миграциях.
- CI проверяет изменения на push и pull request. Публикация Pages
  запускается вручную только для default branch; артефакт содержит лишь
  `dist/`. В frontend-сборку передаются только публичные GitHub Variables.
- Архитектура должна учитывать квоты и ограничения Supabase Free.
  Перед выбором возможностей платформы проверять актуальные ограничения;
  не рассчитывать на неограниченные ресурсы или возможности платного тарифа.
- Обязательные расходы на backend и клиентский хостинг не закладывать.
  Это ограничение хостинга не означает бесплатную регистрацию или
  продление собственного домена.

Схема данных, способ входа, организация модулей, правила доступа и
механизм доставки уведомлений пока не утверждены.

При согласовании основы отдельно рассмотреть:

- Разделение аутентификации и авторизации, хранение ролей и политики RLS.
- Границы браузерного кода, доверенного серверного кода и секретов.
- Миграции БД, генерацию типов и воспроизводимое локальное окружение.
- Организацию клиентских запросов, кеша и обновления данных.
- Навигацию и открытие прямых ссылок TanStack Router с учётом
  статического хостинга GitHub Pages и собственного домена.
- Общую прикладную логику для веб-интерфейса и будущих ботов.
- Надёжное выполнение фоновых задач, повторные попытки и идемпотентность.

Это вопросы для проектирования, а не уже принятые решения.

## Команды и проверки

- `npm ci` — установка зависимостей по lockfile.
- `npm run dev` — локальная разработка, `http://127.0.0.1:5173`.
- `npm run check` — защита секретов, форматирование, lint, types, Vitest,
  production build и повторная проверка артефактов на известные секреты.
- `npm run test:e2e` — Playwright по собранному `dist/`; предварительно
  выполнить `npm run build` и `npx playwright install chromium`.
- `npm run format` — применить Prettier.
- `npm run supabase:start`, `supabase:status`, `supabase:stop` — локальный
  backend; требуется поддерживаемый runtime, например Docker Desktop.
- `npm run supabase:reset` — уничтожает данные только локального стека
  и применяет миграции заново; не выполнять без необходимости.

Сканер секретов проверяет рабочие файлы, подготовленный к коммиту индекс
Git и артефакты `dist/`. Он обнаруживает известные форматы, но не гарантирует
обнаружение произвольного пароля или непрозрачного токена MAX/VK.
Проверка изменений перед коммитом остаётся обязательной.

`prototype/` и `.agents/` исключены из lint, форматирования и тестов
нового приложения; прототип не изменять в рамках сетапа.
Локальные `.tools/`, `.supabase/` и `.superpowers/` игнорируются Git.
