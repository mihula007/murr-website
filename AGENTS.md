# Murr клан — сайт игрового клана

Сайт клана (игра Perfect World) на `https://pwmurr.ru`: заявки и
голосования, события и группы, учёт активности, публикации и рынок,
обсуждения, уведомления, рассылки, администрирование, бот Telegram. Роли —
гость, кандидат, чтец, член, офицер, администратор
([роли](docs/requirements/01-roles.md)). Язык интерфейса, общения и
документации — русский; название в интерфейсе — «Murr клан», заставка —
«MURRCLAN».

Источник правды о поведении — [требования](docs/requirements/README.md);
решения владельца и открытые вопросы — `docs/requirements/17-open-questions.md`;
устройство модулей и их инварианты —
[решения по модулям](docs/architecture/module-decisions.md) (читать раздел
модуля перед его изменением).

## Процесс изменений по запросу сопровождающего (обязательно)

**Решение владельца (14.11.2026).** Сайт запущен. Дальше его развивает
**сопровождающий** — человек без опыта разработки: он не знает, что такое
Git, сборка, выкладка и хостинг, не открывает и не правит файлы, не
запускает команды и не читает код. Любую просьбу изменить, исправить,
обновить или добавить что-то агент выполняет **только** по шагам 0–6 ниже,
не пропуская и не меняя их порядок. Один чат — одно изменение.

### Общение

- Говорить на языке сопровождающего (по умолчанию русский), простыми
  словами, без терминов: не «миграция», «эндпоинт», «коммит», «деплой»,
  а «сохраняю изменения», «выкладываю на сайт». Термин без замены —
  с пояснением в скобках.
- Не просить сопровождающего открыть, прочитать или изменить файл,
  запустить команду, посмотреть код или разницу изменений. Всё это делает
  агент.
- Не задавать технических вопросов (код, схема БД, библиотеки, структура
  API, способ хранения). Технические решения агент принимает сам по
  правилам этого файла. Спрашивать только о поведении, правилах, правах,
  текстах и внешнем виде.
- Технические правила этого файла (обязательный стек, одна Edge Function,
  только Supabase Free и GitHub Pages, защита секретов) сопровождающий не
  меняет. Если просьбу нельзя выполнить в их рамках, объяснить это простыми
  словами и предложить поведение, которое в них укладывается; иначе —
  сказать, что задаче нужен разработчик, и не начинать её.
- Вопрос без просьбы что-то изменить — просто ответ, без шагов процесса.
- Просьба о другом изменении посреди процесса: предложить сначала
  завершить текущее (шаг 6) или отказаться от него, а новое начать в
  новом чате.

### Шаг 0. Подготовка рабочего места

До разговора о сути изменения, молча и без вопросов о технике:

1. Убедиться, что `node --version` — 24 (версия по умолчанию в оболочке
   может быть другой — тогда в каждой команде использовать Node 24 из
   менеджера версий по `.nvmrc`, не установленную рядом).
2. Первым делом, до любых других действий, — `npm run session:prepare`
   (`scripts/session-prepare.ts`). Одна команда делает весь шаг 0 и
   печатает отчёт: `[ok]` — готово, `[!!]` — мешает работе (код выхода 1),
   `[--]` — к сведению. Что она делает:
   - доступ к GitHub (`gh auth status`, `git push --dry-run`; при
     `GH_TOKEN` — `gh auth setup-git`);
   - ветка `main`: переключает на неё, `git fetch`, догоняет `origin/main`
     только fast-forward. Несохранённые или неотправленные изменения и
     расхождение — `[!!]`, ничего не трогает. Вся работа — только в
     `main`: другие ветки и worktree не создавать;
   - Node 24 и `npm clean-install` — только если изменился
     `package-lock.json` или версия Node. Ошибка установки из-за
     несовпадения `package-lock.json` с `package.json` — ошибка
     репозитория, а не повод для `npm install`: сообщить и остановиться;
   - Docker: запускает Docker Desktop, если он не запущен, и стартует
     локальный Supabase **в фоне** — к шагу 4 он готов;
   - `.env`: доступ к Supabase CLI и привязка проекта, переменные выкладки
     (`SUPABASE_DB_PASSWORD`, `AUTH_SMTP_*` — без них выкладка настроек
     сотрёт почту сайта). `TELEGRAM_*` локально не нужны.
     Проверки доступа к GitHub и Supabase кешируются на 7 дней в
     `.tools/session/state.json` (новый токен проверяется заново);
     `-- --force` — проверить всё без кеша.
3. `[!!]` в ветке — сообщить простыми словами и остановиться. Остальные
   `[!!]` и `[--]` о доступе — попросить сопровождающего прислать значение
   **прямо в чат**, по одному, с пошаговой инструкцией простыми словами,
   где его взять (сайт, раздел, какую кнопку нажать). Записать значение в
   `.env` самому, не повторять его в ответах, не записывать никуда, кроме
   `.env`, и повторить `npm run session:prepare -- --force`. Переменные
   для выкладки можно запросить и позже, до шага 6, но до начала шага 6
   они обязательны. Docker не запустился — попросить сопровождающего
   открыть программу Docker Desktop.

### Короткий путь для мелких изменений

Мелкое изменение — текст, подпись, цвет, отступ, порядок элементов,
очевидная ошибка на одной странице без новых прав, данных и списков.
Агент сам решает, что изменение мелкое, и говорит об этом. Тогда:

- шаг 1 — без серии вопросов: сразу шаг 2 с итогом в 2–4 предложения;
  вопросы — только если без них нельзя;
- шаг 3 — требования (если меняются) и код одним коммитом, без плана;
  только затронутые тесты;
- шаги 4–6 — как обычно.

Если по ходу выяснится, что изменение затрагивает права, данные, списки
или несколько страниц, — вернуться к полному процессу и сказать об этом.

### Шаг 1. Выяснение требований

1. Найти в `docs/requirements/` всё, что затрагивает просьба: блоки,
   роли (`01-roles.md`), карту страниц (`02-page-map.md`), решения и
   вопросы (`17-open-questions.md`), реестр списков
   (`docs/architecture/lists.md`). Существующие требования — основа: код
   работает так, как они говорят, без противоречий.
2. Если просьба описывает поведение, которое уже требуется, а сайт
   работает иначе, это ошибка (исправление): требования не меняются, но
   шаги 2–6 обязательны.
3. Задавать вопросы, пока не станет ясно: кто (какие роли) это видит и
   делает; где на сайте (страница, раздел, кнопка); что происходит по
   шагам, включая ошибки, пустые состояния и отмену; тексты и подписи;
   как выглядит на компьютере и на телефоне; кого уведомить; нужно ли
   записывать действие в журнал администратора; что происходит с уже
   существующими данными. Для любого списка — вопрос из раздела «Списки»
   («может ли там быть больше 50 записей?») простыми словами.
4. Вопросы — по одному-три за раз, с готовыми вариантами ответа и
   примерами, где это помогает. Не отвечать за сопровождающего; не
   додумывать поведение, о котором он не сказал, — спросить.
5. Каждое противоречие с существующими требованиями показать простыми
   словами («сейчас правило такое-то, новое ему противоречит») и
   спросить, какое правило остаётся. Итог шага — понятно, какие требования
   добавляются, меняются и удаляются, и между ними нет противоречий и
   «белых пятен».

### Шаг 2. Итог и согласие

До любых изменений кода и документов показать краткое описание простыми
словами: что меняется и для кого; как это будет работать по шагам; как
выглядит; что исчезнет или изменится из того, что есть сейчас (включая
судьбу существующих данных на сайте); что в изменение не входит. Затем
явно спросить: «Утверждаете? Если да — начинаю работу». Начинать только
после явного «да». Любая поправка — вернуться к шагу 1 и показать итог
заново.

### Шаг 3. Требования, реализация, проверки

1. Записать требования в `docs/requirements/` (новые ID, изменённые и
   удалённые пункты по правилам `docs/requirements/README.md`); решения —
   в `17-open-questions.md` как «решение сопровождающего, дата». Обновить
   этот файл, если меняются описанные в нём решения. Сохранить отдельным
   коммитом `docs(requirements): …` в `main`.
2. Крупное изменение (новая страница, раздел или механика) — сначала
   подробный план `docs/superpowers/plans/ГГГГ-ММ-ДД-<тема>.md` по образцу
   существующих, отдельным коммитом. Мелкое — без плана.
3. Реализация — по всем правилам этого файла и навыкам superpowers (TDD,
   проверка перед завершением). Новые таблицы и данные добавить в
   `scripts/seed-dev.ts`, чтобы их можно было проверить на шаге 4.
4. Тесты: unit и компонентные (Vitest), серверные (`npm run test:server`),
   если меняется backend, pgTAP (`npm run supabase:test`), если меняется
   схема, и e2e Playwright на новое поведение — e2e пишутся здесь, а
   запускаются на шаге 6 (весь набор прогоняет CI).
5. Проверки: `npm run check:quick` (секреты, стили, архитектура, формат,
   lint, типы и Vitest только по изменённым файлам; без сборки сайта и
   Storybook — их проверяет CI на шаге 6); серверные и pgTAP — если
   затронуты. Всё зелёное — иначе исправлять, сопровождающему не
   показывать.
6. Коммит в `main` (Conventional Commits). Push — только на шаге 6.

### Шаг 4. Ручная проверка сопровождающим

1. `npm run review:prepare` (`scripts/review-prepare.ts`): дожидается
   локального Supabase, запущенного на шаге 0 (или запускает его),
   применяет новые миграции локально, записывает ключи стека для сайта и
   пересоздаёт тестовые данные. Серверные тесты и e2e очищают таблицы,
   поэтому запускать после них, каждый раз перед показом.
2. Затем в фоне два долгих процесса: `npm run e2e:functions` (выдуманный
   бот, **не** `supabase:functions`: в `.env` рабочий бот Telegram) и
   `npm run dev`. Если они уже запущены с прошлого показа — не
   перезапускать.
3. Сообщить: ссылку `http://127.0.0.1:5173`, логины нужных ролей
   (`seed-admin@example.test`, `seed-officer-1@example.test`,
   `seed-member-1@example.test` и т. п.) и пароль открытым текстом —
   `TEST_PASSWORD` из `tests/server/support.ts`. Это временные данные
   локального стека, показывать их можно. Коды из писем — Mailpit
   `http://127.0.0.1:54324`. Дать короткий список, что проверить, включая
   вид в узком окне браузера (как на телефоне).
4. Предложить ровно два варианта (кнопками, если интерфейс их
   поддерживает, иначе двумя пунктами): **«Принять и выложить на сайт»**
   и **«Есть замечания»**.

### Шаг 5. Замечания

Замечания делаются на месте, одним шагом. Цель максимально упростить и облегчить процесс
внесения правок, чтобы сопровождающий мог быстро получать изменения. Уточняются детали,
если они не ясны, вносятся правки в требования и план, затем имплементируется без запуска
лишних проверок и приложение предоставляется пользователю для ручной проверки и валидации.
В конце предоставляется выбор как после шага 4 с двумя вариантами.

### Шаг 6. Завершение и выкладка

Только после явного «принять» (кнопка или слова). Это согласие владельца
на выкладку этого изменения, включая команды облака с `--yes`; на
откат, принудительный push, удаление данных в облаке и любые действия
вне [инструкции выкладки](docs/operations/deploy.md) оно не
распространяется.

1. Сохранить всё оставшееся коммитом; `git status` чистый; проверить, что
   в коммитах нет секретов (`npm run security:check`).
2. `git push origin main`. CI прогоняет полный `npm run check`, pgTAP,
   серверные тесты и **все e2e** (локально e2e не запускаются).
3. `npm run release` (`scripts/release.ts`) — план без изменений: что
   выкладывается (миграции, настройки, функция `api`, сайт — по разнице
   `origin/public..main`), хватает ли переменных, состояние CI.
4. `npm run release -- --yes` — выкладка по разделу «Обычный выпуск»
   [deploy](docs/operations/deploy.md): ждёт зелёного CI, затем только
   изменившееся — миграции (`--dry-run`, затем выкладка), настройки,
   функция `api`; затем `git push origin main:public`, ждёт «Deploy GitHub
   Pages» и проверяет, что сайт и функция отвечают. Переменные `.env`
   передаёт командам через окружение, не печатая. Красный CI — команда
   останавливается до выкладки: исправить, коммит, push, повторить. Если
   изменился `.env.example`, новые секреты функции задать по deploy.md
   (п. 5) и запускать с `--secrets-checked`.
5. Проверить на `https://pwmurr.ru`, что изменение видно.
6. Остановить локальные процессы (сайт, функции, `npm run supabase:stop`).
7. Сообщить простыми словами: изменение опубликовано и доступно на
   `pwmurr.ru` (может понадобиться обновить страницу). Прямо сказать:
   **«Для следующего изменения начните новый чат».**

Сбой выкладки: не пытаться откатывать без согласия; объяснить простыми
словами, что опубликовано, что нет и чем это грозит, и предложить
решение.

## Секреты: публичный репозиторий

Код публичный. Защита секретов — условие любого изменения, коммита, сборки
и выкладки.

- Реальные секреты — только в `.env` и других игнорируемых env-файлах.
  Никогда — в коде, документации, тестах, логах, сообщениях коммитов,
  артефактах сборки и ответах в чате.
- `.env.example` — шаблон всех ожидаемых переменных без значений. Новая или
  переименованная переменная — сразу в шаблон с пояснением и пометкой,
  обязательна ли она.
- `VITE_*` попадают в браузер и публичны: только URL Supabase и publishable
  key. Серверные ключи, пароли и токены ботов — без `VITE_` и вне
  клиентского кода. Сборка отклоняет неизвестные `VITE_*`.
- Секреты функции в облаке — Supabase Secrets; CI — GitHub Variables
  (публичные) и Secrets.
- Перед коммитом проверить подготовленные изменения. Сканер секретов
  (`npm run security:check`, часть `check`) ловит только известные форматы.
  Утечка — остановить выкладку, сообщить и заменить скомпрометированный
  секрет: удаления из последнего коммита недостаточно.

## Платформа и ограничения

- Клиент — статические файлы React + Vite на GitHub Pages (`pwmurr.ru`).
  Отдельного сервера приложения нет и не будет.
- Backend — только Supabase Free: Postgres, одна Edge Function, Auth,
  Storage, Cron. Никаких обязательных платных сервисов, платных функций
  Supabase или VPS. Перед выбором решения сверять квоты Free
  ([квоты](docs/operations/supabase-free-limits.md)): каждое чтение и
  запись — вызов функции.
- Письма Auth — Resend (SMTP задаётся `config push`, ключ только в `.env`).
- Ветки: разработка — `main`; сайт — `public`, только fast-forward из `main`
  (`git push origin main:public`), прямые коммиты в `public` запрещены.
  Push в `public` запускает «Deploy GitHub Pages».
- Совместимость при выкладке: сначала миграции и функция, потом клиент;
  контракты меняются только совместимо (новые поля необязательны), иначе —
  новая операция рядом со старой. Миграции только вперёд.
- Резервные копии — вручную по [инструкции](docs/operations/backup.md);
  копии с данными не класть в Git.

## Обязательный стек

Одна задача — один инструмент и один способ. Другая библиотека или второй
способ — только по решению владельца-разработчика с причиной, записанной
здесь. Правила с пометкой «проверяет» ловит `npm run check` и CI. Точные
версии — `package.json`; все версии зависимостей точные, установка —
`npm clean-install`.

## Структура кода

- `src/routes/` только объявляет маршруты (hash history: `/#/events`);
  страницы и их логика — `src/features/<домен>/`; провайдеры и сборка —
  `src/app/`; меню и доступ к маршрутам — одна таблица
  `src/app/navigation.ts` (клиентская проверка, не защита данных).
- Общие элементы форм — `src/components/form/`; подтверждение действия —
  `ConfirmActionDialog`; иконка класса — `ClassIcon`; общие модули без
  React — `src/lib/`; ключи кеша домена — `query-keys.ts` рядом с ним.
- Роль клиент берёт только из `account/me`, не из JWT; любой `forbidden`
  перечитывает `me`.
- Сервер: `supabase/functions/api/` — единственная функция с маршрутизацией
  внутри; общий код — `supabase/functions/_shared/`: `<модуль>/service.ts`
  и `<модуль>/repository.ts`, контракты `_shared/contracts/`, БД
  `_shared/db/`, HTTP `_shared/http/`.

## Серверная логика

Вся бизнес-логика — TypeScript в функции `api`. Функции Postgres, RPC,
триггеры и RLS-политики с правилами не пишутся.

- **Слои.** Обработчик HTTP → сервис → репозитории. Сервис проверяет
  исполнителя, роль (из `profiles.access_role` при каждом запросе), состояние
  и ввод, открывает транзакцию и передаёт её репозиториям. SQL — только в
  репозиториях. Связанные изменения, включая аудит и уведомления
  (`notify(tx, …)`), — одна транзакция.
- **Права.** Функция подключается к Postgres напрямую в обход RLS, поэтому
  каждая операция проверяет права в сервисе; тесты — за каждую роль,
  включая запрещённые вызовы.
- **Браузер.** supabase-js — только Auth и вызов функции с JWT. Прикладные
  таблицы закрыты: RLS без политик, GRANT для `anon`/`authenticated` нет.
- **SQL в миграциях** — только схема: таблицы, типы, `NOT NULL`, PK/FK с
  `ON DELETE`, `UNIQUE` (включая частичные против гонок), простые `CHECK`.
  Cron — только вызов `api` по расписанию. Новая ссылка на `profiles`
  обязана получить правило `ON DELETE` и проверку в
  `tests/server/user-deletion.test.ts`.
- **Storage** — приватные buckets, подписанные ссылки после проверки прав,
  тип и размер файла проверяет TypeScript.
- **Время событий** — московское (UTC+3), перевод только
  `@contracts/moscow-time`; «сейчас» — `deps.now()` на сервере.
- **Аудит.** Для каждого нового действия, меняющего состояние, решить
  (вместе с требованиями), пишется ли оно в журнал аудита, и записать
  решение в требованиях.

## Списки

Перед добавлением или изменением любого списка (операция API, возвращающая
массив, и экран с ним) спросить сопровождающего простыми словами: **может ли
список содержать больше 50 элементов?** В вопросе описать экран, кто его
видит, что в строке и как элементы появляются и исчезают со временем. Не
отвечать за сопровождающего; без ответа список считается большим. Ответ записать в реестр
[списков](docs/architecture/lists.md) до реализации.

- **Нет (≤ 50):** всё одним ответом; сервер ограничивает выборку и не
  обрезает список молча; фильтр и поиск на клиенте допустимы.
- **Да (> 50):** курсорная (keyset) пагинация `{ cursor, limit } →
{ items, nextCursor }`, offset и номера страниц не использовать; фильтры,
  поиск, сортировка и итоги — на сервере (у клиента нет всех элементов);
  клиент — `useInfiniteQuery` и виртуализация TanStack Virtual только через
  `src/components/virtual-list.tsx`. Общие поля и тип страницы —
  `_shared/contracts/paging.ts`, курсор — `_shared/http/cursor.ts`.
- Блок под бесконечным списком недостижим: выносить его на вкладку или
  отдельную страницу (пример — вкладка «Чтецы» на странице состава).
- **Исключение — текущие участники клана (Q-48).** Член,
  офицер, администратор — до 200 человек; их списки (состав, участники
  события, проголосовавшие, группы, рейтинг, сводка учёта) всегда целиком
  одним ответом, без курсора и серверных фильтров; поиск и фильтры — на
  клиенте. Сервер ограничивает порогом `MEMBER_LIST_LIMIT` (250) с
  признаком `truncated`; отрисовка — без виртуализации. Чтецы и аккаунты
  под исключение не попадают.
- **Исключение — ленты публикаций и рынка (Q-55).** Больше 50,
  но нумерованные страницы по 50 записей с навигацией по номерам вместо
  курсора и бесконечной прокрутки; поиск, категория и число страниц — на
  сервере, номер страницы — в маршруте. Другие большие списки — курсор.

Подробные правила API и UI и состояние существующих списков —
[docs/architecture/lists.md](docs/architecture/lists.md).

## Дизайн

Угольные поверхности, золотые акценты, светлый текст, фоновое изображение;
подробности — [дизайн-система](docs/design-system.md). Визуальный образец —
прототип `prototype/` (только для чтения, не изменять): новые экраны
сравнивать с ним на 375 и 1240 px.

- Единственная система стилей — Tailwind CSS 4. `src/styles.css` — только
  токены, `@theme` и базовые стили элементов. Никаких своих CSS-классов,
  CSS-файлов, модулей и inline-стилей; исключение — переменные `--virtual-*`
  в `src/components/virtual-list.tsx`. Проверяет `check:styles`.
- Цвета — только токены темы (новый цвет — токен в `:root` и `@theme`);
  стандартная палитра Tailwind отключена. Варианты — `cva`, объединение —
  `cn`, наборы утилит — константы рядом с компонентом.
- Компоненты — `src/components/ui/`, состояния страниц —
  `src/components/states/`, у каждого — история Storybook.
- Каждую страницу и компонент прорабатывать и проверять на узком экране
  (телефон) и на десктопе.

## Команды

- `npm clean-install` — зависимости; `npm run dev` — сайт на
  `http://127.0.0.1:5173`.
- `npm run check` — секреты, стили, архитектура, формат, lint, типы,
  Vitest, сборка, Storybook. `npm run format`, `npm run lint:fix` —
  исправления.
- `npm run supabase:start` / `supabase:stop` — локальный backend (Docker;
  на медленной машине `npx supabase start -x studio`).
  `npm run supabase:reset` уничтожает локальные данные — без нужды не
  запускать.
- `npm run test:server` — тесты сервисов и функции по локальной БД;
  `npm run supabase:test` — pgTAP. Оба и e2e очищают прикладные таблицы.
- `npm run seed:dev` — тестовые данные локального стека для ручной
  проверки.
- Процесс сопровождающего: `npm run session:prepare` (шаг 0),
  `npm run check:quick` (шаг 3), `npm run review:prepare` (шаг 4),
  `npm run release` / `npm run release -- --yes` (шаг 6).
- `npm run supabase:types` — типы БД после миграции; `npm run supabase:env`
  — публичные ключи локального стека для `npm run dev`.
- e2e: `npm run e2e:functions` (функция с выдуманным ботом), затем
  `npm run build:e2e` и `npx playwright test <spec>` — только затронутые
  spec-файлы. На macOS 13 Chromium Playwright не ставится — запускать через
  установленный Google Chrome (`channel: 'chrome'` во временном конфиге).
- `npm run telegram:dev` и `npm run telegram:webhook` переставляют вебхук
  бота: пока в `.env` рабочий бот, не запускать без прямой просьбы.
- Выкладка — только шаг 6 процесса и [инструкция](docs/operations/deploy.md).

`prototype/` и `.agents/` исключены из lint, форматирования и тестов.
Подробности запуска — [README](README.md).
