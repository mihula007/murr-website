# Проект: веб-сайт игровой гильдии

## Назначение и контекст

Веб-приложение для участников гильдии из видеоигры. Название игры и
официальное название проекта пока не уточнены.

Будущие функциональные направления, заявленные владельцем проекта:

- Авторизация и роли: обычный пользователь, офицер, администратор.
- Заявки на вступление, голосование по заявкам и комментарии.
- Личный кабинет с информацией о персонаже.
- Регулярные события и отметки пользователей о присутствии.
- Публикация торговых предложений.
- Сводные таблицы пользователей.
- Интеграции с ботами Telegram, MAX и VK: уведомления и ответы через кнопки.

Это контекст для будущей архитектуры, а не задание реализовать эти функции
на текущем этапе. Матрица разрешений и подробные правила ещё не определены.

## Процесс изменений по запросу сопровождающего (обязательно)

**Решение владельца (14.11.2026).** Сайт запущен. Дальше его развивает
**сопровождающий** — человек без опыта разработки: он не знает, что такое
Git, сборка, выкладка и хостинг, не открывает и не правит файлы, не
запускает команды и не читает код. Любую просьбу изменить, исправить,
обновить или добавить что-то агент выполняет **только** по шагам 0–6 ниже,
не пропуская и не меняя их порядок. Один чат — одно изменение.

### Общение

- Говорить на языке сопровождающего (по умолчанию русский), простыми
  словами, без терминов: не «миграция», «эндпоинт», «коммит», «деплой»,
  а «сохраняю изменения», «выкладываю на сайт». Термин без замены —
  с пояснением в скобках.
- Не просить сопровождающего открыть, прочитать или изменить файл,
  запустить команду, посмотреть код или разницу изменений. Всё это делает
  агент.
- Не задавать технических вопросов (код, схема БД, библиотеки, структура
  API, способ хранения). Технические решения агент принимает сам по
  правилам этого файла. Спрашивать только о поведении, правилах, правах,
  текстах и внешнем виде.
- Технические правила этого файла (обязательный стек, одна Edge Function,
  только Supabase Free и GitHub Pages, защита секретов) сопровождающий не
  меняет. Если просьбу нельзя выполнить в их рамках, объяснить это простыми
  словами и предложить поведение, которое в них укладывается; иначе —
  сказать, что задаче нужен разработчик, и не начинать её.
- Вопрос без просьбы что-то изменить — просто ответ, без шагов процесса.
- Просьба о другом изменении посреди процесса: предложить сначала
  завершить текущее (шаг 6) или отказаться от него, а новое начать в
  новом чате.

### Шаг 0. Подготовка рабочего места

До разговора о сути изменения, молча и без вопросов о технике:

1. Node.js 24 (`node --version`; версия по умолчанию в оболочке может
   быть другой — тогда в каждой команде использовать Node 24 из `nvm`
   по `.nvmrc`, не установленную рядом); затем `npm clean-install` — установка
   зависимостей по `package-lock.json`. Если `package-lock.json` не
   совпадает с `package.json`, это ошибка репозитория, а не повод для
   `npm install`: сообщить и остановиться.
2. Docker Desktop запущен (`docker info`); если нет — запустить его самому
   (`open -a Docker` на macOS) и дождаться готовности. Только если не
   получается — попросить сопровождающего открыть программу Docker Desktop.
3. Наличие `.env` и всех переменных, нужных для разработки и выкладки
   (список и назначение — `.env.example`):
   - доступ к Supabase CLI: `npx supabase projects list` работает, иначе
     нужен `SUPABASE_ACCESS_TOKEN`; проект привязан
     (`supabase/.temp/project-ref`), иначе `npx supabase link --project-ref
fbhndmsmusbqntdymnaz`;
   - `SUPABASE_DB_PASSWORD` — пароль базы облачного проекта для выкладки
     структуры базы;
   - `AUTH_SMTP_*` — без них выкладка настроек сотрёт почту сайта;
   - доступ к GitHub: `gh auth status` и `git push --dry-run origin main`
     проходят, иначе нужен `GH_TOKEN` (затем `gh auth setup-git`);
   - `TELEGRAM_*` локально не нужны: на шаге 4 используется выдуманный бот.
4. Если чего-то не хватает — попросить сопровождающего прислать значение
   **прямо в чат**, по одному, с пошаговой инструкцией простыми словами,
   где его взять (сайт, раздел, какую кнопку нажать). Записать значение в
   `.env` самому, не повторять его в ответах, не записывать никуда, кроме
   `.env`, и проверить, что доступ работает. Переменные для выкладки
   можно запросить и позже, до шага 6, но до начала шага 6 они обязательны.
5. `git status` чистый, ветка `main`, `git pull --ff-only origin main`.
   Незавершённые чужие изменения не трогать — сообщить и остановиться.

3. Задавать вопросы, пока не станет ясно: кто (какие роли) это видит и

4. Вопросы — по одному-три за раз, с готовыми вариантами ответа и

5. Каждое противоречие с существующими требованиями показать простыми

1. Записать требования в `docs/requirements/` (новые ID, изменённые и
   удалённые пункты по правилам `docs/requirements/README.md`); решения —

2. Крупное изменение (новая страница, раздел или механика) — сначала

3. Реализация — по всем правилам этого файла и навыкам superpowers (TDD,

### Шаг 4. Ручная проверка сопровождающим

1. Локальный стек: `npm run supabase:start` (на медленной машине —
   `npx supabase start -x studio`), новые миграции — `npx supabase
migration up` (только локально).
2. Данные: `npm run seed:dev` — пересоздаёт тестовые данные. Серверные
   тесты и e2e очищают таблицы, поэтому запускать после них, каждый раз
   перед показом.
3. Функции — `npm run e2e:functions` (выдуманный бот), **не**
   `supabase:functions`: в `.env` рабочий бот Telegram. Затем
   `npm run supabase:env` и `npm run dev` — оба долгих процесса в фоне.
4. Самому открыть сайт и убедиться, что изменение работает, прежде чем
   звать сопровождающего.
5. Сообщить: ссылку `http://127.0.0.1:5173`, логины нужных ролей
   (`seed-admin@example.test`, `seed-officer-1@example.test`,
   `seed-member-1@example.test` и т. п.) и пароль открытым текстом —
   `TEST_PASSWORD` из `tests/server/support.ts`. Это временные данные
   локального стека, показывать их можно. Коды из писем — Mailpit
   `http://127.0.0.1:54324`. Дать короткий список, что проверить, включая
   вид в узком окне браузера (как на телефоне).
6. Предложить ровно два варианта (кнопками, если интерфейс их
   поддерживает, иначе двумя пунктами): **«Принять и выложить на сайт»**
   и **«Есть замечания»**.

### Шаг 6. Завершение и выкладка

Только после явного «принять» (кнопка или слова). Это согласие владельца
на выкладку этого изменения, включая команды облака с `--yes`; на
откат, принудительный push, удаление данных в облаке и любые действия
вне [инструкции выкладки](docs/operations/deploy.md) оно не
распространяется.

1. Сохранить всё оставшееся коммитом; `git status` чистый; проверить, что
   в коммитах нет секретов (`npm run security:check`).
2. `git push origin main`; дождаться зелёного CI (`gh run watch`). Красный
   CI — исправить и повторить, на сайт не выкладывать.
3. Выкладка по разделу «Обычный выпуск» [deploy](docs/operations/deploy.md):
   миграции (`--dry-run`, затем выкладка), настройки, функция `api`,
   новые секреты — только то, что изменилось; затем
   `git push origin main:public` и зелёный прогон «Deploy GitHub Pages».
   Переменные `.env` передавать командам через окружение, не печатая.
4. Проверить `https://pwmurr.ru`: сайт открывается, изменение видно.
5. Остановить локальные процессы (сайт, функции, `npm run supabase:stop`).
6. Сообщить простыми словами: изменение опубликовано и доступно на
   `pwmurr.ru` (может понадобиться обновить страницу). Прямо сказать:
   **«Для следующего изменения начните новый чат».**

Сбой выкладки: не пытаться откатывать без согласия; объяснить простыми
словами, что опубликовано, что нет и чем это грозит, и предложить
решение.

## Критически важно: публичный репозиторий и секреты

Владелец разрешил публичное размещение исходного кода. Защита секретов —
обязательное условие любых изменений, коммитов, сборок и публикаций.

- Все реальные секреты для локальной разработки записывать в `.env`,
  исключённый из Git через `.gitignore`. Правило распространяется также
  на вложенные env-файлы, варианты окружений и их локальные копии.
- Никогда не записывать значения секретов в исходники, документацию,
  тесты, примеры, логи, сообщения коммитов или публикуемые артефакты.
- В корне обязательно поддерживать `.env.example` — шаблон с названиями
  всех ожидаемых переменных, включая секреты, но без реальных значений.
  Имя `.env.example` задано владельцем; это обычный текстовый шаблон,
  а не зашифрованное хранилище. При добавлении или переименовании
  переменной одновременно обновлять шаблон и пояснение её назначения.
- Пустые значения в шаблоне не означают, что все интеграции обязательны
  для запуска: отмечать переменные будущих или необязательных функций.
- Переменные `VITE_*` включаются в браузерную сборку и являются публичными.
  Допускать в них только публичную конфигурацию, например URL Supabase
  и publishable key. Серверные ключи Supabase, пароли и токены ботов
  никогда не должны иметь префикс `VITE_` или попадать в клиентский код.
- Для опубликованных Edge Functions передавать секреты в защищённое
  хранилище Supabase; локальный `.env` не публиковать вместе с функциями.
  Для CI/CD использовать GitHub Actions Secrets, когда они потребуются.
- Перед коммитом проверять подготовленные изменения и отсутствие
  отслеживаемых файлов с секретами. `.gitignore` не удаляет файлы,
  ранее добавленные в Git. При обнаружении утечки остановить публикацию,
  сообщить владельцу и организовать отзыв или замену скомпрометированного
  секрета; одного удаления значения из последнего коммита недостаточно.

Документация: [переменные Vite](https://vite.dev/guide/env-and-mode),
[секреты Supabase Edge Functions](https://supabase.com/docs/guides/functions/secrets).

## Подтверждённые ограничения и предпочтения

- Обязательное условие архитектуры: backend, включая серверные функции
  и базу данных, должен работать в рамках бесплатного тарифа Supabase.
  Не закладывать обязательные платные сервисы, платные возможности
  Supabase или дополнительный VPS.
- Клиентский хостинг: бесплатный GitHub Pages с подключённым собственным
  доменом `pwmurr.ru` (reg.ru).
- Не предполагать наличие отдельного Node.js-сервера приложения.
- Язык приложения: TypeScript.
- Менеджер пакетов: npm, обычные зависимости в `node_modules`.
- UI: обязательно shadcn/ui (Radix) и Tailwind CSS 4. Tailwind — единственная
  система стилей: собственные CSS-классы компонентов, CSS-модули, отдельные
  CSS-файлы, inline-стили и CSS-in-JS не используются. Подробнее — раздел «Дизайн».
- TanStack обязателен для маршрутизации (Router), серверного состояния
  (Query), форм (Form) и таблиц (Table — с появлением первой таблицы).
  Полный перечень обязательных инструментов — раздел «Обязательный стек».
- Использовать доступные навыки superpowers там, где они применимы.
- Основной язык обсуждения и проектной документации: русский.

## Согласованная основа стека

- React: клиентское веб-приложение.
- Vite: сборка приложения и сервер разработки.
- TanStack Router: маршрутизация клиентского приложения.
- Supabase: backend, серверные функции и база данных в рамках Free.
- GitHub Pages: размещение собранного клиента с собственным доменом.

Выбор React + Vite + TanStack Router принят вместо первоначально
обсуждавшегося Next.js. Причина: клиент размещается как статические
файлы, а backend сосредоточен в Supabase без отдельного сервера.
Next.js и TanStack Start в выбранную основу не входят.

## Инструменты и решения инициализации

- Node.js 24 LTS; версия npm зафиксирована в `packageManager`.
- Все версии прямых npm-зависимостей точные; `package-lock.json` хранится
  в Git. Для воспроизводимой установки использовать `npm clean-install`.
- TypeScript strict с отдельными конфигурациями клиента, инструментов
  Node.js и тестов. Типы Node не добавлять в клиентскую конфигурацию.
- Vitest и React Testing Library — тесты клиентской основы; Playwright
  — браузерные проверки собранного сайта на desktop и mobile.
- Oxlint — линтер. Prettier — форматтер. ESLint не установлен.
  Тела `if`/`else`/`for`/`while`/`do` всегда в фигурных скобках
  (`curly: all` в `.oxlintrc.json`, исправляет `npm run lint:fix`;
  Prettier сам скобки не добавляет).
- TanStack Virtual (`@tanstack/react-virtual`, решение владельца 11.11.2026)
  — виртуализация больших списков, раздел «Списки».

## Списки

**Решение владельца (11.11.2026), обязательно для агентов.** Перед
добавлением или изменением любого списка (операция API, возвращающая
массив, и экран с ним) спросить владельца: **может ли список содержать
больше 50 элементов?** В вопросе описать экран и маршрут, кто его видит,
что в строке и как элементы появляются и исчезают со временем. Не отвечать
за владельца; без ответа список считается большим. Ответ записать в реестр
[списков](docs/architecture/lists.md) до реализации.

- **Нет (≤ 50):** всё одним ответом; сервер ограничивает выборку и не
  обрезает список молча; фильтр и поиск на клиенте допустимы.
- **Да (> 50):** курсорная (keyset) пагинация `{ cursor, limit } →
{ items, nextCursor }`, offset и номера страниц не использовать; фильтры,
  поиск, сортировка и итоги — на сервере (у клиента нет всех элементов);
  клиент — `useInfiniteQuery` и виртуализация TanStack Virtual только через
  `src/components/virtual-list.tsx`. Общие поля и тип страницы —
  `_shared/contracts/paging.ts`, курсор — `_shared/http/cursor.ts`.
- Блок под бесконечным списком недостижим: выносить его на вкладку или
  отдельную страницу (пример — вкладка «Чтецы» на странице состава).
- **Исключение — текущие участники клана (Q-48, 12.11.2026).** Член,
  офицер, администратор — до 200 человек; их списки (состав, участники
  события, проголосовавшие, группы, рейтинг, сводка учёта) всегда целиком
  одним ответом, без курсора и серверных фильтров; поиск и фильтры — на
  клиенте. Сервер ограничивает порогом `MEMBER_LIST_LIMIT` (250) с
  признаком `truncated`; отрисовка — без виртуализации. Чтецы и аккаунты
  под исключение не попадают.
- **Исключение — ленты публикаций и рынка (Q-55, 12.11.2026).** Больше 50,
  но нумерованные страницы по 50 записей с навигацией по номерам вместо
  курсора и бесконечной прокрутки; поиск, категория и число страниц — на
  сервере, номер страницы — в маршруте. Другие большие списки — курсор.

Подробные правила API и UI и состояние существующих списков —
[docs/architecture/lists.md](docs/architecture/lists.md).

## Дизайн

Визуальная основа приложения и Storybook взята из основного прототипа:
угольные поверхности, золотые акценты, светлый текст и фоновое изображение.
Общие токены находятся в `src/styles.css`, компоненты — в `src/components/ui/`,
состояния страниц — в `src/components/states/`. Новые цвета добавлять только
токенами в `:root` с публикацией в `@theme`.

Storybook обязателен: история для каждого компонента `src/components/ui/` и
`src/components/states/`, сборка входит в `npm run check`. Аватар — один
компонент `Avatar` с размерами 40/72/76 px.

Единственная система стилей — Tailwind CSS 4 (решение владельца 11.11.2026).
`src/styles.css` содержит только токены, `@theme` и базовые стили элементов;
собственные CSS-классы компонентов, отдельные CSS-файлы и inline-стили для
оформления не добавлять. Единственное исключение — CSS-переменные
`--virtual-*` с геометрией виртуализации в `src/components/virtual-list.tsx`
(проверяет `check:styles`). Варианты — `cva`, общие наборы утилит — константы
рядом с компонентом, объединение — `cn`. Цвета — только токены темы:
стандартная палитра Tailwind (`bg-red-500`, `text-white`) отключена. Правила
проверяет `npm run check:styles` (часть `npm run check`).

Экранные сценарии и бизнес-логика прототипа не перенесены.
Прототип — визуальный образец: новые экраны сравнивать с ним на 375 и 1240 px.
Подробности: [дизайн-система](docs/design-system.md).

Название приложения в интерфейсе — «Murr клан» (шапка, `<title>`, заглушки).
Исключение по решению владельца 08.11.2026: заставка, как в прототипе,
показывает латинский «MURRCLAN».

При разработке любых страниц и компонентов обязательно прорабатывать
их отображение и взаимодействие на мобильных устройствах и проверять
адаптивность на узком экране вместе с десктопной версией.

## Архитектура и решения

Принятые архитектурные решения:

- Клиент — React-приложение, собираемое Vite в статические файлы для
  GitHub Pages. Серверная логика не выполняется на клиентском хостинге.
- Маршруты объявлены кодом в `src/routes/`; TanStack Router использует
  hash history, например `/#/events` (решение владельца 11.11.2026):
  прямые ссылки работают на Pages без серверных rewrites. Vite `base: './'`
  позволяет использовать собственный домен и путь репозитория.
- Провайдеры и сборка приложения находятся в `src/app/`; доменные модули
  добавляются в `src/features/` вместе с задачами, без пустых абстракций.
- Браузерный клиент Supabase создаётся лениво. Без публичной конфигурации
  возвращается `null`; статический каркас работает без `.env` и сети.
  Сборка отклоняет неизвестные переменные `VITE_*` и серверные ключи.
- Резервное копирование и восстановление — ручные действия администратора по его усмотрению; обязательной периодичности и автоматизации нет. При отсутствии актуальной копии восстановление не гарантируется. Копии с данными не размещать в публичном Git. Инструкция — [backup](docs/operations/backup.md).
- Письма Supabase Auth — Resend на бесплатном тарифе, домен `pwmurr.ru` подтверждён (14.11.2026); SMTP облака задаётся `config push` из `[remotes.production]`, ключ — только в локальном `.env` и настройках проекта, не в клиенте и не в Git. Квоты — `docs/operations/supabase-free-limits.md`.
- Оболочка (этап 2): меню и доступ к маршрутам описаны одной таблицей
  `src/app/navigation.ts`; `RouteGate` показывает «Нет доступа», если роли
  нет в таблице. Это клиентская проверка, не защита данных.
- Роль (этап 3): `AccessProvider` берёт её только из ответа `account/me`
  (профиль в БД), не из JWT и Auth metadata; `status` — `loading`, `guest`,
  `incomplete` (вошёл, регистрация не завершена — права гостя), `ready`,
  `error`. Dev-переключатель ролей удалён; для тестов у провайдера есть проп
  `role`. Демо `/#/dev/unsaved-demo` остаётся только в dev, `e2e/shell.spec.ts`
  проверяет его отсутствие в `dist/`. Кеш TanStack Query очищается при выходе
  и смене пользователя (`SessionProvider`).
- Смена роли во время сессии (этап 4): клиент кеша создаёт
  `createQueryClient` (`src/app/query-client.ts`); любой ответ `forbidden`
  от `api` перечитывает `me`, поэтому меню и доступ обновляются без выхода.
  Иначе `me` перечитывается при возврате на вкладку (после 60 с) и
  перезагрузке; данные всё равно защищены сервером при каждом вызове.
- Сессия в браузере бессрочная до явного выхода или очистки данных сайта
  (Q-35): `persistSession` + `autoRefreshToken`, ограничения сессий Supabase
  не включаются. Регистрация, вход, код, сброс пароля — [проект регистрации](docs/architecture/registration-flow.md).
- Заставка показывается при первом открытии и если последняя активность
  старше 10 минут; метка — `murr-last-activity` в `localStorage` (запасной
  `sessionStorage`). Playwright-сценарии ставят метку через
  `skipSplash` из `e2e/helpers.ts`.
- `useUnsavedChangesGuard(isDirty)` подключать во всех формах, меняющих данные.
- Вход по email и паролю; email и сброс пароля подтверждаются шестизначным
  кодом из письма (`verifyOtp`), без redirect-ссылок, поэтому автоматическая
  обработка Auth redirect остаётся выключенной.
- Вся бизнес-логика — TypeScript в Supabase Edge Functions, данные —
  в Supabase Postgres (решение владельца, см. раздел «Серверная логика»).
  Этап 3: схема `app` (классы, профили, заявки, ссылки, аудит) и одна
  функция `api` с операциями каталога и аккаунта. Этап 4: таблица
  `user_notifications` и модули `applications` (очередь, карточка, прямое
  решение, новая заявка), `roster` (численность, состав, чтецы), `accounts`
  (таблица аккаунтов, смена роли и блокировка, восстановление чтеца),
  `notifications` (`notify(tx, …)` в транзакции действия). Правило даты
  вступления — только `joinedOnAfterRoleChange` в `_shared/membership.ts`:
  переход кандидата или чтеца во внутреннюю роль ставит сегодняшнюю дату по
  Москве, переходы между внутренними ролями и блокировка её не меняют.
  Смена роли блокирует строки всех администраторов, затем цель (`FOR UPDATE`,
  один порядок) — защита основного и последнего администратора от гонок.
  Этап 5: таблицы `votes`, `vote_options`, `vote_ballots` и модуль `votes`
  (список, карточка, создание, правка, голос, завершение, удаление). Итоги
  считаются запросом по голосам, отдельных счётчиков нет. Голос блокирует
  строку голосования `FOR SHARE`, завершение и удаление — `FOR UPDATE`:
  голос не проходит после завершения. Голосование по заявке создаётся только
  `applications/submit-to-vote`; завершение и удаление меняют статус заявки
  в той же транзакции, окончательное решение — `applications/final-decide`
  (только администратор). Ключи кеша клиента — `query-keys.ts` модулей
  `votes` и `applications`, чтобы модули сбрасывали кеш друг друга без цикла.
  Этап 6: таблицы `events`, `event_attendance`, `event_templates` и модуль
  `events`. Всё время событий — московское (UTC+3 без перехода, Q-08, Q-44):
  перевод только `@contracts/moscow-time`, показ — `formatDateTimeMsk`;
  «ближайший выпуск» и «событие началось» считает сервер по `deps.now()`.
  Ответ — одна строка `(event_id, user_id)`, только до начала (Q-43), под
  блокировкой события `FOR SHARE`, в аудит не пишется (Q-45). Правка и
  удаление: автор-офицер, любой офицер для постоянных выпусков без автора
  (Q-47), администратор. Постоянные события создаёт задание Supabase Cron
  `events-ensure-weekly` (понедельник 00:00 МСК) вызовом `api` с заголовком
  `x-cron-secret` (`EVENTS_CRON_SECRET`, адрес и секрет — в Supabase Vault)
  или запасная кнопка офицера; дубликат исключён `UNIQUE (recurring_preset,
starts_at)`.
  Этап 7: таблицы `event_groups`, `event_group_members`, `group_templates`
  (+ группы и участники шаблона), `event_activity_records`; модули `groups`
  и `activity`. Участник — в одной группе события (PK `(event_id, user_id)`),
  лидер — признак строки участника (частичный `UNIQUE`), поэтому перенос
  или удаление не оставляет лидера вне группы. Операции групп блокируют
  событие `FOR UPDATE` и отклоняют закрытое (`state_conflict`), в аудит не
  пишутся (Q-54). `events/close` в одной транзакции пишет итог посещения
  (текущий состав и все, кто в группах: в группе — «Посетил», вне группы с
  ответом — «Не посетил», без ответа — «Не отметился»; ник и класс
  копируются), отметку закрытия и аудит; повторное закрытие — `state_conflict`.
  Закрытое событие и его группы неизменяемы и не удаляются (FK `RESTRICT`).
  Аналитика считается запросами по итогу: процент — посещения / записи
  участника (Q-49), период — по дате начала МСК (Q-50); чтецы остаются в
  истории и сводке, но не в рейтинге (Q-53). Шаблоны групп — общая
  библиотека офицеров и администраторов, не больше 20 (GRP-12).
  Этап 8: таблицы `publications`, `publication_attachments`, `market_listings`
  и модули `publications`, `market` (права раздельные: публикации — офицер
  свои, администратор любые; рынок — член и офицер свои, администратор любые).
  Содержимое — JSON Tiptap, проверяемый только `@contracts/rich-text`
  (Q-57); `search_text`, `excerpt`, `cover_url` вычисляет сервис при
  сохранении. Снятие с публикации возвращает в черновики; правка с
  `expectedUpdatedAt`, другая версия — `state_conflict`. Вложения — приватный
  bucket `publication-images`, загрузка в `uploads/<userId>/`, проверка
  сигнатуры при привязке, удаление файлов после коммита. Чужой черновик —
  `not_found`. Аудит: создание, изменение, публикация, снятие и удаление
  (категории `publications`, `market`; в `details` — id, заголовок,
  категория, статус).
  Этап 9: таблицы `discussion_threads` (одна строка на родителя: событие,
  голосование, публикация или объявление; `CHECK` одного родителя, каскад
  от родителя), `discussion_messages`, `discussion_reactions`,
  `discussion_reads` и модуль `discussions`. Доступ к ветке следует
  родителю (`discussions/parents.ts`): писать можно в незавершённые событие
  и голосование, в опубликованный материал с включённым обсуждением; запись
  блокирует родителя `FOR SHARE`. Прочтение — одна отметка «прочитано до»
  на пользователя и ветку. Упоминания `@ник` и ответы — уведомления
  `discussion_mention`/`discussion_reply` через `notify`. Открытая ветка
  опрашивает `discussions/changes` раз в 30 с только при видимой вкладке
  (Q-58), Realtime не используется; аудита нет (Q-63). Ветка грузится
  страницами вверх (`ReverseVirtualList` в `virtual-list.tsx`).
  Этап 10: таблица `section_views` (отметка просмотра раздела на пользователя)
  и операции `notifications/*` в модуле `notifications`. Колокольчик —
  кандидат и внутренние роли; панель — последние 50 (Q-64), прочтение — по
  одному или «прочитать все». Шапка опрашивает одну операцию
  `notifications/summary` (непрочитанные + счётчики разделов) раз в 60 с при
  видимой вкладке (Q-66). Новизна раздела — объекты чужих авторов после
  отметки; первая отметка ставится при первом доступе (Q-67). Новые источники
  `notify`: группа и пати-лидер (источник — событие, одно на участника),
  смена роли; ответы на событие автору не приходят (Q-65). Главная внутренних
  ролей берёт события из `events/list` (тот же кеш, что расписание), топ —
  `activity/month-top`, состав — `roster/list`; отдельной операции нет.
  Прочтения и отметки просмотра в аудит не пишутся.
  Этап 11: таблицы `broadcast_drafts`, `broadcast_templates`, `user_deletions`
  и модули `broadcasts`, `deletion`. Рассылки — только подготовка (Q-22):
  текст из события, голосования или группы составляет `broadcasts/prefill`,
  черновики и шаблоны общие для офицеров и администраторов (не больше 50 и
  20, Q-69, Q-70), файлы — только метаданные. Администрирование: поиск и
  сортировка аккаунтов на сервере, карточка, смена пароля другого аккаунта
  через Auth Admin API (Auth сам завершает сеансы цели, Q-72), журнал
  (`audit/list`, курсор). Безвозвратное удаление (Q-73–Q-75) — только
  не-администратора: служебная запись без FK на профиль → файлы Storage →
  одна транзакция (черновики, профиль с каскадами и `SET NULL`, аудит с ником
  и email) → Auth; каждый этап отмечается, повтор кнопкой продолжает с места
  сбоя. Пока запись есть, `loadActor` возвращает `deleted`, любой вызов —
  `account_deleted`, клиент выходит локально. Новая ссылка на `profiles` в
  миграции обязана получить правило `ON DELETE` по таблице данных плана
  этапа 11 и проверку в `tests/server/user-deletion.test.ts`.
  Этап 13 (Telegram, Q-76–Q-96, [проект](docs/architecture/telegram-integration.md)):
  таблицы `telegram_links`, `telegram_link_codes`, `telegram_announcements`,
  `telegram_event_messages`; модуль `telegram` и отправка в `broadcasts`.
  Вебхук бота — маршрут `telegram/webhook` той же функции `api`, проверка —
  заголовок `X-Telegram-Bot-Api-Secret-Token`; Bot API — через `fetch`
  (`_shared/telegram/gateway.ts`), токен не логируется. Без
  `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` и `TELEGRAM_WEBHOOK_SECRET`
  интеграция выключена (`telegram_unavailable`). Привязка — одноразовый код
  `t.me/<бот>?start=` (хеш, 15 минут), один Telegram на аккаунт. Анонс
  события — с кнопками ответа; ответ кнопкой и с сайта — одна функция
  `saveAnswer` (`events/service.ts`); у участника активно одно сообщение на
  событие (прежнее теряет кнопки); ответ на сайте перерисовывает его фоново
  (`_shared/background.ts`, `EdgeRuntime.waitUntil`; локально нужен
  `[edge_runtime] policy = "per_worker"`). Одна запись аудита на отправку;
  привязка, отвязка и ответы в аудит не пишутся. Вложения рассылок отменены
  (Q-82), текст — до 3800 символов (Q-91). ВКонтакте и MAX не подключены.
- Прикладные таблицы не открываются через Data API: браузер не получает
  к ним GRANT, RLS включён без политик (запрет по умолчанию).
- Ветки (решение владельца 14.11.2026): разработка — в `main` (default
  branch), опубликованный сайт — ветка `public`, домен `pwmurr.ru`. Выпуск —
  только fast-forward `public` из `main`, прямые коммиты в `public` запрещены.
  CI проверяет изменения на push и pull request. Push в `public` (или ручной
  запуск на ней) публикует Pages; workflow повторяет `npm run check` без
  e2e (им нужен локальный Supabase) и загружает только `dist/`. В
  frontend-сборку передаются только публичные GitHub Variables.
- Архитектура должна учитывать квоты и ограничения Supabase Free.
  Перед выбором возможностей платформы проверять актуальные ограничения;
  не рассчитывать на неограниченные ресурсы или возможности платного тарифа.
- Обязательные расходы на backend и клиентский хостинг не закладывать.
  Это ограничение хостинга не означает бесплатную регистрацию или
  продление собственного домена.

## Серверная логика

**Решение владельца (08.11.2026):** вся бизнес-логика находится в одном
месте — в TypeScript. Функции Postgres/RPC не пишутся. Доступ к данным
строится по паттерну Repository с абстракциями над SQL. Решение заменяет
прежние предложения о RPC, триггерах и RLS-политиках как носителях правил.

Что из этого следует (обязательно, решение владельца 11.11.2026):

- **Где код.** Edge Functions (Deno) в `supabase/functions/`. Общий код —
  `supabase/functions/_shared/`: подключение к БД и транзакции, проверка
  сессии и роли, HTTP-ошибки, доменные модули `<модуль>/service.ts`
  (правила, права, аудит) и `<модуль>/repository.ts` (SQL). Будущие боты
  вызывают те же сервисы. Edge Function ровно одна — `api` с маршрутизацией
  внутри (экономия холодных стартов и квоты). Новая функция — только по
  решению владельца с причиной, записанной в этом файле.
- **Слои.** Обработчик HTTP → сервис → репозитории. Сервис проверяет
  исполнителя, роль, состояние и ввод, открывает транзакцию и передаёт её
  репозиториям (unit of work). Репозиторий — единственное место с SQL;
  сервисы SQL не пишут. Связанные изменения, включая аудит, — одна
  транзакция БД, открытая в TypeScript. Построитель запросов — Kysely
  (только репозитории и `_shared/db/`), драйвер — postgres.js
  (`postgres` через `kysely-postgres-js`, только `_shared/db/`).
- **Подключение к БД.** Прямое подключение Postgres из Edge Function
  (`SUPABASE_DB_URL`, пул соединений). Такое подключение обходит RLS,
  поэтому каждая операция обязана проверить права в сервисе; проверка
  покрывается тестами для каждой роли, включая запрещённые вызовы.
- **Браузер.** supabase-js используется только для Auth (регистрация,
  код, вход, сессия) и вызова Edge Functions с JWT пользователя. Чтение и
  запись прикладных данных — только через Edge Functions. Роль берётся из
  `profiles.access_role` на сервере при каждом запросе, не из Auth metadata.
- **Что остаётся в SQL.** Только схема в миграциях: таблицы, типы,
  `NOT NULL`, PK/FK с правилами `ON DELETE`, `UNIQUE` (включая частичные
  индексы, защищающие от гонок) и простые `CHECK` как страховка
  целостности. Задания Supabase Cron допустимы только как вызов функции
  `api` по расписанию (этап 6), без правил в SQL. Функций, процедур,
  триггеров и RLS-политик с правилами нет; RLS включён без политик, GRANT для `anon`/`authenticated` не выдаются.
- **Storage.** Приватные buckets; доступ выдают Edge Functions после
  проверки прав (подписанные ссылки на загрузку и чтение), проверка типа и
  размера файла — в TypeScript.
- **Тесты.** Сервисы и репозитории — Vitest на Node по локальной БД
  (`npm run test:server`, общий код не использует глобалы Deno), там же
  HTTP-тесты функции за каждую роль; pgTAP (`npm run supabase:test`) — что
  Data API-роли не имеют доступа к таблицам и ограничения работают;
  Playwright — сценарии. Версии пакетов в `supabase/functions/api/deno.json`
  совпадают с `package.json` (проверяется тестом).
- **Лёгкий старт функции.** В Edge Functions не импортировать
  `@supabase/supabase-js`: Auth и Storage вызываются через `fetch` (этап 3:
  холодный старт 3,2 → 0,9 с локально). Новые зависимости функции проверять
  на время холодного старта.
- **Совместимость при выкладке.** Сначала применяются миграции и функции,
  затем публикуется клиент; изменения контрактов — только совместимые
  (новые поля необязательны), иначе новая операция рядом со старой.
- **Квоты Free.** Каждое чтение и изменение — вызов Edge Function: учитывать
  лимит вызовов, CPU-время и память функций Free и перепроверять их перед
  выбором решения.

Схема данных растёт по этапам, правила доступа остальных разделов и
механизм доставки уведомлений пока не утверждены. Матрица ролей и
функциональные контракты находятся в `docs/requirements/`; решения
владельца и оставшиеся вопросы — в `docs/requirements/17-open-questions.md`.
При добавлении любого действия, меняющего состояние системы, явно
определять, должно ли оно записываться в журнал аудита; фиксировать
решение в требованиях и реализовывать соответствующее событие аудита,
если действие подлежит аудиту.

При согласовании основы отдельно рассмотреть:

- Разделение аутентификации и авторизации, хранение ролей и проверку прав
  в сервисах Edge Functions.
- Границы браузерного кода, доверенного серверного кода и секретов.
- Миграции БД, генерацию типов и воспроизводимое локальное окружение.
- Организацию клиентских запросов, кеша и обновления данных.
- Навигацию и открытие прямых ссылок TanStack Router с учётом
  статического хостинга GitHub Pages и собственного домена.
- Общую прикладную логику для веб-интерфейса и будущих ботов.
- Надёжное выполнение фоновых задач, повторные попытки и идемпотентность.

Это вопросы для проектирования, а не уже принятые решения.

## Команды и проверки

- `npm clean-install` — установка зависимостей по lockfile.
- `npm run dev` — локальная разработка, `http://127.0.0.1:5173`.
- `npm run check` — защита секретов, правила стилей и архитектуры,
  форматирование, lint, types, Vitest, production build, повторная проверка
  артефактов на известные секреты и сборка Storybook.
- `npm run check:architecture` — SQL только в репозиториях, история для
  каждого компонента ui/states, одна Edge Function.
- `npm run supabase:test` — pgTAP-тесты схемы (нужен запущенный стек).
- `npm run test:server` — тесты сервисов, репозиториев и функции `api` по
  локальному Supabase; сам запускает `supabase functions serve`, если нужно.
- `npm run seed:dev` — пересоздать тестовые данные локального стека
  (`scripts/seed-dev.ts --reset`) для ручной проверки.
- `npm run supabase:types` — типы БД в `supabase/functions/_shared/db/`.
- `npm run supabase:env` — публичные URL и ключ локального стека в
  `.env.development.local` для `npm run dev` (файл игнорируется Git).
- `npm run build:e2e` и `npm run test:e2e` — Playwright по сборке,
  подключённой к локальному Supabase; перед тестами запустить
  `npm run e2e:functions` (функции с выдуманным ботом и фальшивым Bot API
  `e2e/fake-telegram.ts`, его поднимает Playwright). Коды из писем читаются из Mailpit.
  Локально один worker (слабая машина владельца), в CI — два.
- `npm run admin:bootstrap -- --email … --nickname … --name … --class …` —
  однократное назначение первого администратора (Q-32).
- `npm run telegram:dev` — туннель `cloudflared` и вебхук тестового бота
  (рядом — `npm run supabase:functions`); `npm run telegram:webhook` —
  вебхук рабочего бота на облачную функцию.
- `npm run format` — применить Prettier.
- `npm run supabase:start`, `supabase:status`, `supabase:stop` — локальный
  backend; требуется поддерживаемый runtime, например Docker Desktop. На
  медленной машине Studio может не пройти health check — тогда
  `npx supabase start -x studio`.
- `npm run supabase:reset` — уничтожает данные только локального стека
  и применяет миграции заново; не выполнять без необходимости.

Сканер секретов проверяет рабочие файлы, подготовленный к коммиту индекс
Git и артефакты `dist/`. Он обнаруживает известные форматы, но не гарантирует
обнаружение произвольного пароля или непрозрачного токена MAX/VK.
Проверка изменений перед коммитом остаётся обязательной.

`prototype/` и `.agents/` исключены из lint, форматирования и тестов
нового приложения; прототип не изменять в рамках сетапа.
Локальные `.tools/`, `.supabase/`, `.superpowers/` и `.claude/` (настройки Claude Code, например `launch.json`) игнорируются Git.
